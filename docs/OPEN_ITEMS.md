## 2. 머지 직후 바로 할 것 — **실사용자가 지금 겪는 것**

### 2-1. 🔴 한마디가 올린 사람에게만, 그것도 맨 아래에만 보인다

주최자 화면에서 한마디가 사진 밑에 안 붙고 앨범 맨 아래에만 나온다.
자리: `backend/app/api/album.py` 의

```python
visible_photos = [photo for photo in all_photos if not document_photo_ids or str(photo["id"]) in document_photo_ids]
```

앨범 문서에 적힌 사진만 보이므로, **문서가 만들어진 뒤에 더해진 사진·한마디는 사라진다.**

PO 결정(A안):
- 한마디는 **올리는 즉시** 자기 사진 밑에 붙는다. 주최자·참여자 화면 모두 동시에.
- 사진은 **앨범 맨 뒤**에 붙는다(맨 위가 아니다 — 아이폰에서 맨 위로 갔다).
- 안내글: **"앨범을 만든 분이 나중에 한 번에 정리해서 앨범을 다시 만들어요."**
- 나중에 주최자가 한 번에 반영한다. 자동으로 다시 만들지 않는다.

★ `share.py` 의 `is_pending_photo` · `is_pending_memory` 는 **건드리지 않는다.**
  공유 화면은 이미 이 규칙대로 돌고 있다 — 주최자 화면만 다르다.

## 2-3. ★ 속도는 dev 에서 잴 수 없다 (2026-08-13 · 함정)

```
운영 DB   woorialbum       ap-southeast-1 (싱가포르)
개발 DB   woorialbum-dev   ap-northeast-2 (서울)      ← 다르다
Railway   asia-southeast1  (싱가포르)  · 운영·dev 같음
```

dev 는 **서버가 싱가포르, DB 가 서울**이다. 질의마다 바다를 건너므로 dev 의
`질의당 750ms` 와 운영의 `질의당 70ms` 는 나란히 놓을 수 없다.
실제로 그렇게 비교해서 "고친 쪽이 더 느리다"는 잘못된 결론을 한 번 냈다.

**규칙: 속도 판정은 운영 로그로만 한다.** 기준 지표 하나로 고정한다 —
`POST /api/auth/bootstrap` 의 **첫 호출**. 고치기 전 운영 값은 **1259ms**
(2026-08-13 02:39, 이어지는 호출은 180ms).

Railway 는 배포 단위로만 로그를 주므로 **이전 배포의 로그는 남지 않는다.**
before 값을 재려면 고치기 전에 미리 적어 두어야 한다.

남은 선택지(지금은 안 한다): dev DB 를 싱가포르에 새로 만든다. 리전은 변경이
안 되고 새 프로젝트를 만들어야 한다. 개발 편의를 위한 일이라 순서가 뒤다.

## 7. 관리자 대시보드 10초 — 두 번 훑던 것을 한 번으로 (2026-08-13 · 고침)

질의가 느린 게 아니라 **저장소를 두 번 훑는다.** 경로가 `albums/<앨범>/photos/<사진>/`
이라 사진 하나가 폴더 하나고, `list_recursive` 는 폴더마다 LIST 를 한 번씩 보낸다.
`count_orphan_files` 가 `albums` 밑을, `storage_usage` 가 버킷 전체를 **각각** 훑는다.
사진 53장에 약 150회 순차 왕복 = 10.1초. 사진 500장이면 1000회를 넘는다.

고치는 법 (동작을 바꾸지 않는 쪽): 버킷 전체 훑기는 `albums` 밑을 포함하므로
**한 번만 훑고 두 계산이 그 목록을 나눠 쓴다.** 두 함수에 `files` 인자를 선택으로
받게 하고 `admin_service` 만 한 번 훑어 넘긴다. CLI(`operations_cli`) 는 그대로 둔다.
→ 왕복 절반. 그래도 사진 수에 비례하는 성질은 남는다. 근본은 저장소 훑기를
   대시보드에서 떼는 것(별도 버튼/주기 작업)이지만 MVP 에서는 안 한다.

**고침 — 커밋 `b95ff6d`.** 위 방법 그대로. `count_orphan_files` · `storage_usage` 가
`files` 를 선택으로 받고, `admin_service` 가 버킷을 한 번 훑어 둘에 넘긴다. 인자를 안
주면 지금까지처럼 스스로 훑으므로 `operations_cli` 는 한 줄도 안 바뀌었다.
`orphan_count` · `stored_count` · `bytes` · `file_count` 가 수정 전과 같은 값인지 검사로
고정했고, 대시보드를 한 번 그릴 때 `list_recursive` 가 **한 번만** 불리는지도 고정했다
(`tests/test_admin_dashboard_storage_scan.py`). 저장소가 막히면 0 으로 두고 대시보드는 뜬다.

★ **남는 한계는 그대로다** — LIST 횟수는 여전히 사진 수에 비례한다. 왕복이 절반이 됐을
   뿐이고, 사진이 크게 늘면 다시 느려진다. 근본 해법(대시보드에서 훑기를 떼는 것)은
   여전히 안 했다.

## 10. 왜 한 번 말한 것이 안 고쳐졌나 — 원인 둘 (★ 근본)

### 10-1. 끝난 것을 안 적었다

`K-QUEUE`(26) · `J-QUEUE`(17) = 43항목 중 **완료 표시가 붙은 것이 2개뿐**이었다.
실제 커밋은 39개. 끝난 것을 안 적어서 무엇이 남았는지 아무도 몰랐다.
→ 각 항목에 완료 커밋 해시를 적어 넣는 작업이 남아 있다.

### 10-2. 🔴 테스트가 결함을 고정하고 있었다

`tests/urgentRegression.test.ts:376` 이 이렇게 적혀 있었다:

```
assert.match(sheet, /navigator\.clipboard\.writeText\(await url\(\)\)/)
```

아이폰에서 링크 복사가 **안 되던 그 코드 모양**을 "이렇게 있어야 한다"고 박아둔 것이다.
고치면 테스트가 깨지니 되돌리게 된다 — **사람이 안 고친 게 아니라 고치면 벌을 받았다.**
`caf1e36` 에서 뒤집었다.
**전수 조사 결과 (2026-08-13) — 같은 것은 더 없다.**

`frontend/tests` · `backend/tests` 전체에서 🔴·결함·버그 표시가 달린 검사 아홉 자리를
하나씩 봤다. `urgentRegression` 말고는 전부 **고친 모양**을 고정하고 있다
(`copyTextFromPromise` · `<AlbumShareSheet` · `resolveShareImageUrl` ·
`pdfFailureMessage(`). 그것은 제 일을 하는 검사다. 알려진 나쁜 모양
(`writeText(await` · `innerHTML` · 배열을 의존 목록에 넣는 `useEffect`)을 붙잡는
단언도 하나도 없다.

**다만 결이 다른 위험이 셋 남아 있다.** 아래는 *동작*이 아니라 **소스 문자열 한 줄**을
그대로 붙잡는다. 지금은 통과하지만, 동작이 같은 정상적인 손질(도우미로 빼기·이름
바꾸기)에도 깨진다. 그때 검사 문구만 보면 **"고친 것을 되돌려야 통과한다"** 고 읽히기
쉽다 — 결함을 고정한 것과 같은 사고가 이 길로도 난다.

| 파일 | 붙잡고 있는 것 |
| --- | --- |
| `captionSave.test.ts:75` | `item.id === saved.id ? { ...item, caption: saved.caption }` 표현식 그대로 |
| `preparePaintYield.test.ts:96` | `setPreparingProgress({ done: settledCount, total: limited.length });` 호출 그대로 |
| `uploadFormRender.test.ts:45` | `showsSelectionCount(photos.length) && !isPreparing ?` JSX 조건 그대로 |

★ **이번에 고치지 않았다** (목록만 내라고 했다). 고칠 때는 문자열을 붙잡는 대신
  마운트해서 결과를 보는 쪽으로 바꾼다 — 셋 다 그렇게 바꿀 수 있는 자리다.

## 규칙

1. 대화에서 "나중에" 라고 말한 것은 **그 자리에서** 이 파일에 적는다.
2. 작업 커밋에 이 파일 갱신을 함께 담는다.
3. 작업 시작 전에 0·1·2번부터 본다.
4. **코드로 판정 안 되는 것은 재고 나서 고친다.** 짐작으로 고치면 또 남는다.
5. **"별건으로 잡자" 라고 쓰지 않는다.** 그 말이 그동안 사라짐의 통로였다.
