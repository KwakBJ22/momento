# 참여·반응·방명록 설계 (제안)

작성 2026-08-01. **확정.** 6항의 결정 사항 반영 완료. DB 구조와 앨범 구조가 바뀐다.

## 배경

앨범을 만드는 사람만이 아니라 **구경하고 반응하는 사람**이 앨범을 풍성하게 만든다.
지금은 참여 경로가 "함께 만들기" 하나뿐이라, 사진을 더할 생각이 없는 방문자는 남길 자리가 없다.

---

## 1. 역할 규칙

| | 얻는 경로 | 열람 | 사진 추가 | 사진별 기억 | 방명록 | 반응 | 제목·에필로그 편집 | 앨범 삭제 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **주인** | 앨범 생성 | O | O | O | O | O | O | O |
| **함께 만드는 사람** | 초대 링크 | O | O | O | O | O | X | 본인 것만 |
| **보러 온 사람** | 감상 링크 | O | X | X | O | O | X | 본인 것만 |

- 로그인 없이도 모든 참여가 가능하다 (현행 유지). guest session 기준.
- 권한 검사는 **백엔드에서** 수행한다.

### 링크 종류를 백엔드가 판단해야 한다

현재 프런트가 URL 패턴(`isContributionInviteUrl`)으로 감상/초대를 구분한다.
이는 권한 판단을 프런트에 맡기는 것이라 원칙에 어긋나고 쉽게 깨진다.

→ `share_links.kind` 컬럼 추가 (`view` | `contribute`). 기존 행은 `contribute` 로 backfill.

### "함께 만들기 시작" 버튼 제거

`CollaborationPanel` 의 이 버튼은 `collaboration_enabled` 플래그만 켠다.
초대 링크를 만들어 보내는 행위 자체가 이미 의사표시이므로 앞단계 버튼은 불필요하다.

- 초대 링크를 처음 요청할 때 자동으로 켠다.
- **참여 중단 수단은 반드시 남긴다.** 링크가 잘못 퍼졌을 때 되돌릴 방법이 필요하다.

## 2. 반응 (이모지)

### 현재 상태

백엔드는 이미 완성돼 있고 **UI 만 없다.**

- `share_reactions` 테이블, `POST /api/public/shares/{token}/reactions`
- `api.ts` 의 `submitShareReaction()`
- 종류: `remember` / `warm` / `smile`
- `session_hash` 로 중복 방지

### 반드시 고쳐야 할 것 — 반응이 링크에 묶여 있다

`share_reactions.share_link_id` 는 **공유 링크**를 가리킨다. 링크는 재발급·비활성화가 가능하다.
링크를 새로 만들면 반응이 이전 링크에 남아 흩어지고, **앨범 단위 집계가 불가능해진다.**

앨범 인기 순위로 쓰려면 `album_id` 기준이어야 한다.

→ `share_reactions.album_id` 추가 (NOT NULL, `albums` 참조). `share_link_id` 는 유입 경로 기록용으로 nullable 유지.
→ 중복 방지 키를 `(album_id, session_hash, reaction)` 으로 변경.
→ **지금 반응 데이터가 0건이라 마이그레이션 비용이 없다. 데이터가 쌓이면 비싸진다.**

### 이모지 종류 (제안)

Momento 는 SNS 가 아니라 포토북이다. "좋아요 경쟁" 으로 보이면 안 된다.
그래서 **3종 이하**, 감정이 서로 겹치지 않게, 한국 사용자에게 직관적인 것으로 고른다.

**확정: 3종.**

| 순서 | 이모지 | 라벨 | 코드 | 역할 |
| --- | --- | --- | --- | --- |
| 1 | ❤️ | 좋아요 | `love` | 가장 보편적. 카카오톡 문화에 익숙. 인기 지표의 주력 |
| 2 | 🥹 | 뭉클해요 | `moved` | 추억·그리움. Momento 의 정체성에 해당하는 감정 |
| 3 | 😊 | 웃음이 나요 | `smile` | 즐거움. 아이·일상 사진에 자연스럽다 |

기존 `remember` / `warm` / `smile` 과 비교하면 `smile` 은 유지, `remember`·`warm` 이
`love`·`moved` 로 바뀐다.

**왜 3종인가 (검토 기록)**

`👍 추천해요`, `👏 멋져요` 를 더한 4~5종 안을 검토했으나 채택하지 않았다.

- `좋아요` / `추천해요` / `멋져요` 는 의미가 겹친다. 좋다고 느낀 사용자가 셋 중
  무엇을 누를지 고민하게 된다. 반응은 0.5초 안에 눌러야 하는 행위이고, 고민이 생기면 안 누른다.
- `추천해요` / `멋져요` 는 콘텐츠를 **평가**하는 말이다. 커뮤니티 톤이지 포토북 톤이 아니다.
  가족 사진에 "추천해요" 는 어색하다.
- 겹치는 반응은 인기 집계 신호를 흐린다. 같은 "좋다" 가 셋으로 쪼개지면 앨범 간 비교가 애매해진다.
- 카카오톡 웹뷰 360px 폭에서 이모지+라벨 4개는 글자가 눌린다. 3개가 여유롭다.

**인기 집계는 3종을 동등하게 합산한다.** 하트만 세면 나머지가 장식이 된다.

### 표시 규칙

- 반응은 **익명 집계만** 보여준다. 누가 눌렀는지 표시하지 않는다.
  포토북에 사회적 압력을 들이지 않기 위해서다.
- 앨범 단위 반응을 먼저 붙인다. **사진별 반응은 출시 후** — 사진 30장 × 3종이면 화면이 시끄럽고,
  앨범 단위 반응이 실제로 쓰이는지 먼저 확인하는 게 맞다.

## 3. 방명록

앨범 전체에 남기는 짧은 글. 사진별 "기억" 과 구분된다.

| | 사진별 기억 | 방명록 |
| --- | --- | --- |
| 대상 | 사진 하나 | 앨범 전체 |
| 남기는 사람 | 함께 만드는 사람 | 보러 온 사람 포함 누구나 |
| 표시 위치 | 해당 사진 아래 | 앨범 마지막 |
| 테이블 | `photo_memories` | **신규 필요** |

`guest_memory_submissions` 는 게스트가 남긴 것을 나중에 계정에 연결하는 claim 흐름용이라 용도가 다르다.

→ 신규 테이블 `album_guestbook_entries` (album_id, contributor_id, author_name, message, created_at, deleted_at).
   기존 쿼리를 건드리지 않으므로 컬럼 확장보다 안전하다.

### 앨범 구조에 미치는 영향

CLAUDE.md 6항의 앨범 구조는 "변경 금지" 로 되어 있다. 방명록은 그 구조에 **추가**되는 요소다.

```
월 → 날짜 → 사진 → 캡션 → "YYYY.MM.DD의 이야기" → … → "우리의 이야기"
                                                          → [반응]
                                                          → [방명록]   ← 신규
```

"우리의 이야기" **다음**에 배치한다. 앨범 본문이 끝난 뒤 사람들이 남긴 흔적이 오는 순서다.
**CLAUDE.md 6항도 함께 갱신해야 한다.**

- 글자 수 상한은 사진 기억(500자)보다 짧게. 200자 제안.
- **PDF 에는 포함하지 않는다 (확정).** 인쇄물은 앨범 본문만 담는다. 방명록은 웹에서 계속
  쌓이는 성격이라 인쇄 시점에 잘리면 어색하다.
- **작성 시 이름을 필수로 받는다 (확정).** 기존 참여 흐름이 이름을 받으므로 일관된다.

## 7. 공개 범위 (2026-08-01 확정)

### 이미 있는 것

```
albums.visibility   text NOT NULL DEFAULT 'family'
                    CHECK (visibility IN ('private','family'))
albums.family_id    uuid
families / family_members / family_invitations   테이블 존재
```

공개 범위의 뼈대는 이미 스키마에 있다. 화면에 노출된 적이 없을 뿐이다.
`families` 는 현재 계정당 개인 그룹 1개가 자동 생성되는 용도로만 쓰인다.

### 결정

| 항목 | 결정 |
| --- | --- |
| 전체공개(public) | **넣지 않는다** |
| 친구 관계(요청·수락·차단) | **만들지 않는다** |
| 그룹 | 기존 `families` 를 **"내 사람들"** 로 재활용 |
| 앨범별 초대(함께 만들기) | 현행 유지 — 앨범마다 |

### 전체공개를 뺀 이유

- 주 콘텐츠가 가족·아이 성장 사진이다. 인터넷에 공개되면 검색엔진에 노출되고 회수가 불가능하다.
- 개인정보처리방침 9항("자녀 사진 공유 시 전달 범위를 신중히")과 충돌한다.
- 아동 관련 규제 리스크가 생긴다.
- 앨범 인기 순위는 **내 앨범들 사이의 순위**이므로 전체공개가 필요 없다.
- 기존 CHECK 제약이 `private`/`family` 뿐인 것도 원 설계에서 의도적으로 뺀 흔적으로 보인다.

### 친구 관계를 만들지 않은 이유

친구는 소셜 그래프다. 요청·수락·목록·차단·해제가 한 묶음이고, 들어오는 순간
Momento 는 포토북에서 소셜 네트워크로 성격이 바뀐다. CLAUDE.md 1항과 정면으로 부딪힌다.

풀어야 할 실제 문제는 **"앨범마다 공유를 다시 눌러야 하는 번거로움"** 이고,
그건 기존 `families` 로 해결된다. 한 번 초대해 두면 새 앨범이 자동으로 그 사람들에게 열린다.

### 공개 범위 값

| 값 | 이름 | 볼 수 있는 사람 |
| --- | --- | --- |
| `private` | 나만 보기 | 소유자만 |
| `family` | 내 사람들에게 공개 (기본) | 내가 초대해 둔 사람들 |
| `link` | 링크가 있는 사람 | 공유 링크를 받은 사람 |

- `link` 값만 추가하면 된다. 공유 링크를 발급하면 `link` 로 자동 전환한다.
- **계정 단위 기본값 설정은 만들지 않는다.** `visibility` 기본값이 이미 `family` 라
  "내 사람들" 에 초대해 두면 새 앨범이 자동으로 열린다. 목적이 달성되므로 설정 화면이 불필요하다.

### "내 사람들" 규칙

- 수락 절차를 따로 만들지 않는다. **초대 링크를 열면 합류**한다.
  링크를 여는 행위 자체가 수락이므로 별도 화면이 필요 없다.
- **차단은 없다.** 다만 소유자가 **목록에서 제거**하는 수단은 반드시 있어야 한다.
  잘못 들어온 사람을 뺄 방법이 없으면 안 된다. 차단(관계 단절)과는 성격이 다르다.
- `family_members.status` 에 이미 `invited`/`active`/`left`/`removed` 가 있다. 그대로 쓴다.
- `family_invitations` 는 이메일 기반으로 설계돼 있으나 이 서비스는 카카오 기반이다.
  `token_hash` 를 이용한 **링크 초대**로 쓴다. 이메일 발송은 만들지 않는다.

### 두 축은 직교한다

- `albums.visibility` — **누가 접근할 수 있나**
- `share_links.kind` — **접근한 사람이 무엇을 할 수 있나** (열람 / 함께 만들기)

그래서 1~3단계와 충돌하지 않는다. `kind` 가 먼저 정리돼 있어야 이 층이 깔끔하게 얹힌다.

### 원칙

- **이름은 DB 허용 목록을 기준으로 통일하고, TODO.md 를 거기에 맞춘다.**
  새 이름이 꼭 필요하면 CHECK 제약을 확장하는 migration 을 함께 만든다.
- 지표 계산에 필요한 최소 집합만 붙인다. 14개를 다 붙이지 않는다.
- 개인 식별 정보를 이벤트에 넣지 않는다 (`event_logger` 의 기존 허용 키 정책을 따른다).
