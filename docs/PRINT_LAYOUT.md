# 인쇄 레이아웃 설계

작성 2026-08-01. 판형·그리드·레이아웃 규칙의 단일 출처.
`DESIGN_SYSTEM.md`(화면 UI)와 별개다. 이 문서는 **앨범 지면**을 다룬다.

## 왜 이 문서가 필요했나

지금까지 웹 화면 레이아웃을 그대로 A4 에 밀어 넣어 PDF 를 만들었다.
웹은 세로로 무한히 흐르는 매체이고 인쇄물은 **고정된 면을 채우는 매체**다.
원리가 달라서 "사진만 뒤죽박죽 얹어 놓은" 결과가 나왔다.

벤치마킹 결과 모든 포토북 서비스가 **정사각 판형**을 기본으로 쓴다.
Once Upon 20×20·27×27, Snaps 8×8인치, CEWE 15×15부터. A4 는 문서 규격이지 포토북 판형이 아니다.

---

## 1. 판형 (확정)

| 항목 | 값 |
| --- | --- |
| 재단 후 크기 | **200 × 200mm** (정사각) |
| 재단 여백(bleed) | 각 면 **3.18mm** |
| **문서 크기** | **206.36 × 206.36mm** |
| 안전 영역 | 재단선 안쪽 12.7mm → **174.6 × 174.6mm** |
| 해상도 | **300 DPI** |
| 문서 픽셀 | 2437 × 2437px |

### 정사각인 이유

- 모바일 사진은 세로·가로가 섞여 있다. 정사각 지면이면 둘 다 어색하지 않게 앉는다.
  A4 처럼 세로로 긴 면에는 가로 사진이 초라해 보인다.
- 펼치면 400×200mm 가 되어 가로 사진을 시원하게 쓸 수 있다.
- 업계 표준이다. 인쇄 업체 선택지가 넓다.

### 화면용 PDF 도 같은 판형을 쓴다

사용자가 화면에서 본 것과 인쇄물이 같아야 한다.
정사각 PDF 를 A4 프린터로 뽑으면 위아래 여백이 생길 뿐 문제되지 않는다.

### MAX_EDGE 검증

전면 사진에 필요한 픽셀은 2437px. 현재 업로드 상한 `MAX_EDGE = 2560` 으로 **통과한다**(여유 123px).
단 27×27cm 이상으로 판형을 키우려면 3265px 이 필요하므로 `MAX_EDGE` 를 먼저 올려야 한다.
이미 업로드된 사진은 되돌릴 수 없다.

## 2. 그리드

| 항목 | 값 |
| --- | --- |
| 지면 여백 | **15mm** (사방) |
| 콘텐츠 영역 | **170 × 170mm** |
| 사진 사이 간격 | **5mm** |
| 2열 폭 | 82.5mm |
| 3열 폭 | 53.3mm |

### 두 종류의 배치

| | 쓰는 곳 | 규칙 |
| --- | --- | --- |
| **여백형** | 대부분의 지면 | 15mm 여백 안에 사진 배치 |
| **전면형(full-bleed)** | 표지, 강조 사진 | 사진이 재단선을 넘어 bleed 까지 나간다 |

전면형에서는 사진의 **가장자리 3.18mm 가 잘려 나갈 수 있다.**
인물의 얼굴이나 중요한 요소가 가장자리에 있는 사진은 전면형에 쓰지 않는다.

### 글자는 언제나 안전 영역 안

캡션·날짜·이야기 등 모든 텍스트는 **재단선 안쪽 12.7mm 안**에 있어야 한다.
지금 캡션이 페이지 경계에 붙어 잘리는 문제가 이 규칙으로 해결된다.

## 3. 사진 배치 원칙

### 자르지 않는다

`CLAUDE.md` 의 "사진 원본 비율 유지" 원칙을 지킨다.
Once Upon 은 고정 크롭 비율을 쓰지만, 우리는 자르지 않는다.

대신 **사진 방향에 맞는 레이아웃을 고른다.** 세로 사진에는 세로 슬롯을, 가로 사진에는 가로 슬롯을 준다.
그러면 자르지 않고도 지면이 정돈된다. 슬롯 안에서는 `contain` 이며 여백이 생겨도 괜찮다.

방향 판정은 DB 의 `width`/`height` 로 한다. 화면에서 추측하지 않는다.

### 프레임

화면에서는 흰 프레임(패딩 10px + 얇은 선 + 약한 그림자)을 쓴다.
**인쇄물에서는 지면 여백 자체가 프레임 역할을 하므로 흰 프레임을 쓰지 않는다.**
종이 위의 그림자는 인쇄되면 지저분해 보인다.

### 기울기

화면의 ±2° 기울기는 **인쇄에서 0으로 한다.** 재단 오차와 겹치면 실수처럼 보인다.

## 4. 레이아웃 종류

Once Upon 이 10종으로 충분하다고 판단했다. 우리도 그 규모로 간다.
**사용자는 레이아웃을 새로 짜지 않는다. 주어진 것 중에서 바꿔볼 수만 있다.**

| # | 이름 | 사진 | 구성 |
| --- | --- | --- | --- |
| 1 | `cover` | 1 | 표지. 전면 사진 + 제목 + 기간 |
| 2 | `full` | 1 | 전면 사진 (bleed). 강조용 |
| 3 | `single` | 1 | 여백 안 사진 1장 + 캡션 |
| 4 | `pair-row` | 2 | 가로 2열. 세로 사진 2장에 적합 |
| 5 | `pair-stack` | 2 | 세로 2단. 가로 사진 2장에 적합 |
| 6 | `trio-row` | 3 | 가로 3열 |
| 7 | `trio-focus` | 3 | 큰 1장 + 작은 2장 |
| 8 | `quad` | 4 | 2×2 |
| 9 | `story` | 0 | 날짜 이야기 전용 지면 |
| 10 | `ending` | 0 | "우리의 이야기" 마무리 |

### 선택 규칙

같은 날짜의 사진 수와 방향에 따라 자동으로 고른다.

```
1장  → 세로면 single, 가로면 single 또는 full
2장  → 둘 다 세로면 pair-row, 둘 다 가로면 pair-stack, 섞이면 pair-stack
3장  → 방향이 같으면 trio-row, 섞이면 trio-focus
4장  → quad
5장 이상 → 4장씩 나눠 quad 반복, 나머지는 위 규칙
```

한 지면에 **최대 4장**이다. 그 이상은 사진이 우표만 해진다.

## 5. 페이지 구성

```
표지                      cover
날짜별 사진 지면들          single / pair / trio / quad
  각 날짜 마지막에         story  ("YYYY.MM.DD의 이야기")
마무리                    ending ("우리의 이야기")
```

- **반응과 방명록은 인쇄에 포함하지 않는다** (확정 사항).
  인쇄물은 앨범 본문이고, 그것들은 웹에서 계속 쌓이는 성격이다.
- 날짜 이야기가 짧으면 사진 지면 하단에 넣고, 길면 별도 지면(`story`)으로 뺀다.
- **사진과 그 캡션은 절대 페이지 경계를 넘지 않는다.** 한 덩어리로 다음 면에 넘긴다.

### 페이지 수

포토북은 제본 때문에 보통 4의 배수이고 최소 페이지 수가 있다.
**인쇄 업체 선정 후 확정한다.** 그전까지는 제약을 두지 않는다.

## 7. 구현 방향

### 현재 방식은 인쇄에 쓸 수 없다

`html2canvas` + `jsPDF` 는 화면을 사진 찍는 도구다. 구조적 한계가 있다.

| 문제 | 원인 |
| --- | --- |
| 사진 왜곡 | `object-fit` 미지원 |
| 페이지에서 잘림 | 화면 전체를 한 장으로 래스터화 후 자름 |
| 192 DPI 고정 | canvas 해상도 = scale × 96 |
| 글자가 흐림 | 텍스트가 벡터가 아니라 이미지 |
| CMYK·bleed 불가 | — |

### 서버 사이드 렌더링으로 전환한다

```
인쇄 전용 라우트  /print/{albumId}?token=...   (서명 토큰, 짧은 만료)
  → 기존 AlbumRenderer 를 인쇄 모드로 렌더. 네비·버튼 없이.
백엔드가 Headless Chromium 으로 그 URL 을 열고 page.pdf() 호출
결과를 Storage 에 저장 + 서명 URL 반환 (기존 캐시 흐름 유지)
```

- 진짜 브라우저 엔진이라 CSS 를 완전히 지원한다. `@page`, `break-inside`, `object-fit` 이 정상 동작한다.
- 텍스트가 벡터로 들어간다.
- 사진이 원본 해상도로 임베드된다.
- 서버에서 생성하므로 기기별 차이가 없고 모바일 메모리와 무관하다.
- **같은 `AlbumRenderer` 를 재사용하므로** "웹/공유/PDF 는 동일한 렌더러" 원칙이 오히려 더 잘 지켜진다.

### PDF 캐시 주의

현재 `getAlbumPdfUrl(albumId, albumVersion)` 이 캐시를 먼저 준다.
**나쁜 PDF 가 한 번 만들어지면 `album_version` 이 바뀔 때까지 계속 배포된다.**
렌더링 방식을 바꿀 때 캐시 키에 렌더러 버전을 포함시켜야 한다.

## 8. 무료 PDF의 브랜드 요소 (2026-08-05 PO 결정)

**PDF 는 사용자가 서비스 밖으로 들고 나가는 유일한 물건이다.** 종이는 집에 남고,
카카오톡 링크는 스쳐 지나간다. 그래서 여기에 돌아올 길을 심는다.

### 두 종류로 나뉜다

| 요소 | 무료 PDF (화면·공유용) | 인쇄용 PDF (유료) |
| --- | --- | --- |
| 마지막 페이지 브랜드 소개 | ✅ | ❌ |
| QR 코드 | ✅ | ❌ |
| "우리도 만들어볼까?" 문구 | ✅ | ❌ |
| 워터마크 | ✅ (단, 시점 주의 — 아래) | ❌ |

**돈 주고 만든 포토북 마지막 장에 우리 광고가 있으면 안 된다.**
인쇄소에 넘기는 파일에는 이 요소들이 들어가지 않는다.

이 구분이 그대로 유료화 경계가 된다 — *"기능을 잠그는"* 것이 아니라
*"소유권이 완성된다"*. 무료로도 다 만들고 PDF도 받지만 우리 이름이 남고,
돈을 내면 온전히 사용자 것이 된다.

### QR 코드 — 어디로 보내는가가 핵심

| 보내는 곳 | 판단 |
| --- | --- |
| 서비스 홈 | 약하다. "광고구나" 하고 끝난다 |
| **이 앨범** | **채택.** 종이 → 화면 → 참여로 이어진다 |

인쇄물을 본 사람이 QR 을 찍으면 그 앨범이 웹에서 열린다. 사진을 확대하고,
기억을 읽고, **자기 사진을 얹을 수 있다.** 이것이 우리 바이럴의 가장 강한 형태다.

> **⚠️ 반드시 지킬 것 — QR 은 끊을 수 있는 별도 링크로 발급한다.**
> 지금 공유 링크(`/s/…`)는 **만료가 없다.** 그대로 인쇄물에 박히면
> 그 종이를 잃어버렸을 때 되돌릴 방법이 없다.
> 인쇄용 QR 은 별도 토큰으로 발급하고 소유자가 언제든 끊을 수 있어야 한다.
> 이걸 나중에 고치려면 이미 인쇄된 종이는 손댈 수 없다.

### 워터마크 — 원리는 맞지만 시점이 있다

**없앨 방법이 있어야 정당하다.** 지금은 유료 플랜도 인쇄 상품도 없어서,
워터마크를 만난 사용자에게 *"이걸 없애려면 어떻게 하나"* 에 대한 답이 없다.
그러면 그냥 품질이 낮은 서비스로 보인다.

→ **인쇄 상품 출시와 같이 넣는다.** 시범운영 중에는 이르다.

**넣을 때도 사진 위는 피한다.**

| | |
| --- | --- |
| 사진 위 반투명 로고 | 어머니 사진에 로고가 겹친다. **선물을 못 한다** |
| **여백·페이지 하단** | 출처 표시로 읽힌다. 사진은 온전하다 |

이미 `.album-renderer__brand-footer` 가 있으므로 그것을 조금 더 또렷하게 하는
정도면 충분하다.

### 구현 시점

**전부 200×200mm 판형 재작성 때 함께 넣는다.** 지금 붙이면 두 번 만든다.
(워터마크만 인쇄 상품 출시 시점으로 한 번 더 미룬다.)
