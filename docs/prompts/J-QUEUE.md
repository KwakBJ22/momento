## J-1. 🔴 아직도 `30장 중 0장`에 오래 머문다 [조사 완료 e7d71c2 — 결과는 J-1b]

F-3(`ab4438f`)에서 고친 뒤에도 그대로다. **무엇이 나아졌는지 사용자가 못 느낀다.**

### ★ 원인을 단정하지 않는다 — 먼저 재서 보고할 것

F-3 이 고친 것은 "화면이 숨겨지면 준비가 멈춘다"였다. **화면을 보고 있을 때 느린
것은 그때 안 고쳤다.** 지금 증상은 그쪽일 수 있다.

- 사진 30장으로 **실제 시간을 잰다.** 화면을 계속 보고 있는 상태로.
  - `0장`에 머무는 시간
  - 숫자가 한 번 오르는 데 걸리는 시간
  - 전체가 끝나는 시간
- 그 시간이 **어디서 나가는지** 나눠서 잰다 — 읽기 / 크기 줄이기 / 올리기 / 그 밖.
- ★ **먼저 재서 보고하고 멈춘다.** 어디를 고칠지는 그 숫자를 보고 정한다.

### 고칠 때 지킬 것 (미리 못박아 둔다)

- ★ **가짜 진행률을 만들지 않는다.** 시간으로 밀어 올리지 않는다.
- ★ **단계 문구를 늘리지 않는다.** `크기를 줄이고 있어요` 같은 내부 사정은 말하지 않는다.
- 첫 숫자가 뜨기까지 걸리는 시간이 문제라면, **동시에 준비하는 장수**를 손대기 전에
  한 장이 왜 그렇게 걸리는지부터 본다.

## J-1b. `0장`을 보여주지 않는다 · 첫 한 장을 먼저 끝낸다

J-1 측정 결과에 대한 답이다. **굽는 시간을 줄이는 쪽으로 가지 않는다.**
한 장의 89%가 이미지를 펴고 굽는 일이면 그건 폰이 하는 일의 하한에 가깝다.
품질(0.85)·`MAX_EDGE`(2560)·동시 장수(2)는 **전부 그대로 둔다.**

고칠 것은 **화면이 사실을 말하는 방식**이다.

### 1-b-1. 아직 한 장도 안 끝났으면 숫자를 보여주지 않는다

```
지금                              바꿀 것
사진을 준비하고 있어요 · 30장 중 0장    사진을 준비하고 있어요
                                  (첫 장이 끝나면)
                                  사진을 준비하고 있어요 · 30장 중 1장
```

- ★ `0장`은 정보가 아니라 **불안**이다. 0 은 "아무 일도 안 일어나고 있다"로 읽힌다.
  실제로는 일하고 있는데 화면이 그것을 부정하고 있다.
- ★ **가짜가 아니다.** 숫자를 지어내는 것이 아니라, **아직 셀 것이 없을 때 안 세는 것**이다.
  `1장`이 뜨는 순간은 정말로 한 장이 끝난 순간이다. 지금과 똑같다.
- 문구는 `사진을 준비하고 있어요` 한 줄 그대로. **단계 문구를 늘리지 않는다.**

### 1-b-2. 첫 한 장은 혼자 준비한다

지금은 동시에 2장이라 **둘이 거의 같이 끝난다.** 그래서 첫 숫자가 뜨기까지
한 장 시간이 아니라 **두 장 몫의 경합 시간**을 기다린다(측정: 569~762ms, 한 장 289~330ms).

- ★ **첫 묶음만 1장으로 한다.** 그 뒤부터는 지금처럼 2장씩.
- 첫 숫자가 대략 **절반 시간에** 뜬다. 그 뒤 `1 → 3 → 5 …` 로 오른다.
- ★ 전체 시간은 거의 그대로다(첫 장 하나만 늦게 겹치기 시작한다).
- ★ 동시 장수 2 는 그대로다. 메모리 경고가 붙어 있는 값이라 올리지 않는다.

### 지킬 것

- ★ **가짜 진행률을 만들지 않는다.** 시간으로 밀어 올리지 않는다.
- ★ **단계 문구를 늘리지 않는다.** `크기를 줄이고 있어요` 같은 내부 사정은 말하지 않는다.
- 품질 · `MAX_EDGE` · 동시 장수를 **건드리지 않는다.**

### 회귀 테스트

- ★ 한 장도 안 끝났으면 **`N장 중 0장`이 화면에 없을 것**
- ★ 한 장이 끝나면 `1장`이 뜰 것 — 그 시점이 **실제 완료 시점**일 것
- ★ 첫 묶음이 1장일 것 / 그 뒤 묶음은 2장일 것
- 숫자가 시간으로 움직이지 않을 것 / 단계 문구가 늘지 않을 것

### 기록해 둘 것 (고치지 않는다)

- **PNG(화면 갈무리)는 1.7배 든다.** 투명도 검사로 화소를 한 번 더 훑는다.
  사진첩 사진은 대개 JPEG 이라 지금은 드물다. 시범운영에서 캡처를 많이 올리면 그때 본다.
- **EXIF 가 파일을 통째로 읽는다**(앞 64KB 만 필요). 5~7ms 라 지금 고칠 값이 아니다.
- ★ **숨겨진 탭에서는 `toBlob` 이 말도 안 되게 느려진다.** 800px 한 장에 1초가 나왔다.
  시간을 잴 때는 **반드시 보이는 창**에서 잰다. 이것이 F-3 결함이 그토록 심했던
  이유이기도 하다 — 화면이 숨겨지면 프레임만 안 오는 것이 아니라 굽는 일 자체가 느려진다.

## J-2. 🔴 `한마디`라는 말이 두 곳에서 다른 뜻이다 [완료 bd33d04]

사진 고르기 화면에 이렇게 적혀 있다.

> 사진마다 짧은 **한마디**를 남기면 더욱 생생하고 풍성한 앨범이 완성됩니다. (선택)

여기서 받는 것은 **캡션**이다(§7). 그런데 `한마디`는 §7에서 **참여자가 사진에 남기는
말**의 이름이다. 같은 말이 두 가지를 가리키면 "아까 한마디 썼는데 또?"가 된다.

### 캡션을 사용자에게 부르는 이름 = **`한 줄`** (§7 16차)

`캡션`은 기술 용어라 쓰지 않는다(§8). `한 줄`은 짧고 부담이 없고 `한마디`와 겹치지 않는다.

### 문구

> **사진마다 한 줄 적어두면 앨범이 훨씬 풍성해져요.** (선택)

- `완성됩니다` → `풍성해져요`. 명령이 아니라 얻는 것을 말한다(§10).
- `(선택)`은 남긴다. 안 써도 된다는 것을 알아야 부담이 없다.

### 강조

지금 본문 회색이라 눈에 안 들어온다.

| | 값 |
| --- | --- |
| 본문 | `--c-text` · **굵게(600)** · 지금 크기에서 **+1단계** |
| `(선택)` | `--c-text-soft` · 굵기 보통 · **지금 크기 그대로** |

- ★ 브랜드색을 쓰지 않는다. 이 자리는 버튼이 아니다.
- ★ 배경·테두리를 넣지 않는다(§11 — 알림 껍데기는 배경이 없다).

### 함께 볼 것

★ **다른 자리에서도 캡션을 `한마디`라고 부르는 곳이 있는지 규칙으로 훑는다.**
목록으로 주지 않는다 — 예전에 목록으로 줬다가 15곳이 남았다.
`한마디`가 나오는 자리마다 **그것이 캡션인지 한마디인지** 보고 캡션이면 `한 줄`로 바꾼다.

## J-6. `대표사진 바꾸기`에서 고른 것이 잘 안 보인다 [완료 c12103d]

지금은 얇은 테두리 하나뿐이다. 사진이 많으면 어느 것을 골랐는지 한눈에 안 들어온다.

| | 값 |
| --- | --- |
| 테두리 | **3px** `--c-brand` (지금보다 두껍게) |
| 배지 | 우상단에 **체크(`✓`) 원** — 지름 28px, 배경 `--c-brand`, 글자 흰색 |
| 배지 여백 | 사진 모서리에서 8px |

- ★ **색만으로 구분하지 않는다.** 체크 배지가 있어야 색약인 사람도 안다
  (I-5b 와 같은 규칙).
- ★ **고르지 않은 사진을 흐리게 하지 않는다.** 사진이 가장 중요하다(§6).
  고른 것을 도드라지게 할 뿐, 나머지를 죽이지 않는다.
- 사진 고르기 화면의 `대표사진` 배지와 **같은 모양**을 쓴다. 두 곳이 달라 보이면 안 된다.

**회귀 테스트** — 고른 사진에 체크 배지가 있을 것 / 고르지 않은 사진이 흐려지지 않을 것

## J-7. 🔴 `한마디 쓰기`가 화면마다 다른 것을 연다

앨범을 만든 직후 화면에서 `한마디 쓰기`를 눌러 글을 남겼더니 **캡션 자리에 들어가 있었다.**
사진 밑에 작성자 이름과 함께 한마디로 남아야 한다(§7).

### 확인한 것 — 진입점이 셋이고 서로 다르다

```
AlbumView.tsx:728        onAddMemory → 우리가 남긴 말로 스크롤
AlbumResult.tsx:259      onAddMemory → openEpilogueEditor    ← `우리의 이야기` 편집창
PublicShareView.tsx:404  onAddMemory → openContribution("memory")   ← 이것만 §4에 맞다
```

§4 는 **`한마디 쓰기`가 여는 것 = 사진에 다는 한마디**로 정해져 있다.
세 곳 중 둘이 다른 것을 연다. **I-2(공유하기 다섯 자리)와 같은 병이다** —
한 행동에 자기 나름의 구현이 여럿(§11).

### ★ 먼저 재현해서 보고할 것

- 앨범 만든 직후 화면에서 `한마디 쓰기` → 글을 쓰면 **어디에 저장되는가?**
  `album_photos.caption` 인가 `photo_memories` 인가.
- 실제 요청 본문을 보고 확인한다. 화면만 보고 짐작하지 않는다.
  (캡션이 조용히 죽었던 G-1 이 그래서 안 잡혔다.)

### 고칠 것

- ★ **세 화면 모두 `한마디 쓰기`는 같은 것을 연다** — 사진 목록에서 사진을 고르고
  그 사진에 한마디를 남긴다. 저장은 `photo_memories`.
- ★ **주최자도 한마디를 쓸 수 있다**(§7 권한표 — 읽기·쓰기 전원).
  주최자라고 `우리의 이야기` 편집으로 보내지 않는다.
- `우리의 이야기` 편집은 그 글 옆의 진입점으로만 간다. 하단 네비에서 열지 않는다.
- `우리가 남긴 말`은 본문 맨 아래에서 스크롤로 만난다. 네비 칸을 쓰지 않는다(§4).
- ★ **저장된 한마디에는 작성자 이름이 붙는다.** 캡션에는 안 붙는다(§9).
  이 둘이 화면에서 구별되어야 한다.

### 회귀 테스트

- ★ 세 화면의 `한마디 쓰기`가 **같은 것**을 열 것
- ★ 거기서 쓴 글이 `photo_memories` 로 갈 것 — **요청 본문을 확인**할 것
- ★ 저장된 한마디에 작성자 이름이 보일 것 / 캡션에는 안 보일 것
- 하단 네비에서 `우리의 이야기` 편집이 열리지 않을 것

## J-8. 🔴 참여 중단 뒤 참여자 화면을 확인하지 않았다

주최자가 `참여 중단`을 누르면 이런 문구가 뜬다.

> 참여를 중단했어요. **기존 초대 링크로는** 더 이상 사진·한마디를 남길 수 없어요.

### 확인한 것 — 문구가 사실과 다르다

`collaboration_status = "closed"` 가 되고, 백엔드는 **이미 참여 중인 사람까지 전부** 막는다.

```
collaboration_service.py:538   status == "closed" → 403 "더 이상 추가할 수 없어요"
share_service.py:60            closed → 참여 불가 사유
collaboration.py:725           closed → 403
```

링크 문제가 아니다. **주최자가 사실과 다른 것을 읽고 누른다**(§11 — 성공하지 않았는데
성공 문구를 띄우지 않는다. 여기서는 **일어난 일을 축소해서 말한다**).

### ★ 먼저 확인해서 보고할 것

1. **로그인한 참여자가 `/album/:id` 로 들어올 때** `can_contribute` 가 false 로
   내려가는가? `get_album_access` 가 `collaboration_status` 를 보는가?
   - 안 본다면 **버튼은 그대로 있고 누르면 403** 이다 — H-1 과 똑같은 모양이다.
2. 공유 링크(`/s/`)로 들어온 참여자는 어떻게 되는가?
   (`contribution_block_reason` 은 보고 있으니 그쪽은 될 가능성이 높다)
3. 두 경로가 **다르게 동작하면** 그 자체가 결함이다 — 판정은 한 곳이어야 한다(§1).

### 고칠 것

- ★ **참여가 끝난 앨범에서는 참여자도 구경꾼 화면을 본다.**
  `resolveAlbumRole` 이 이미 `can_contribute` 로 판정하므로, **백엔드가 그 플래그를
  제대로 내려주면** 화면은 저절로 맞는다. 프런트에서 따로 추측하지 않는다(§11).
- ★ **왜 그런지 한 줄 알려준다.** 아무 설명 없이 버튼만 사라지면 고장으로 보인다.

  > 이 앨범은 사진과 한마디를 다 모았어요. 지금은 보기만 할 수 있어요.

  - 안내 껍데기(§9 — 배경 없음, 글머리 없음)를 쓴다.
  - **이미 남긴 사진과 한마디는 그대로 보인다.** 지워지지 않는다.
- **주최자 문구를 사실대로 고친다.**

  > 참여를 마쳤어요. 이제 아무도 사진과 한마디를 더할 수 없어요.
  > 다시 받고 싶으면 `함께 만들자고 보내기`로 새로 초대하면 돼요.

  - ★ 되돌릴 수 있는지 먼저 확인하고 적는다. **되돌릴 수 없으면 그 문장을 쓰지 않는다.**
  - 되돌릴 수 없다면 누르기 전에 한 번 묻는다(되돌릴 수 없는 것은 확인 단계를 둔다 — §5).

### 회귀 테스트

- ★ `closed` 인 앨범에서 참여자에게 **사진 추가·한마디 버튼이 없을 것**
- ★ 로그인 참여자(`/album/:id`)와 링크 참여자(`/s/`)가 **같게 동작할 것**
- ★ 이미 남긴 사진·한마디가 그대로 보일 것
- 주최자 문구가 실제 동작과 같을 것

## J-9. 🔴 열리지 않는 링크가 이유를 말하지 않는다

카카오톡 대화방의 메시지는 **지워지지 않고 계속 남는다.** 몇 달 뒤에도 눌린다.
죽은 링크를 누르는 일은 예외가 아니라 **정기적으로 일어나는 일**이다.

그런데 지금은 네 가지 다른 사정이 한 문장으로 뭉친다.

```
collaboration_service.py:178-190   없음 / 만료 / 사용 횟수 초과 / 무효화  → 전부 None
collaboration_service.py:195       → "초대 링크를 찾을 수 없거나 만료되었습니다."
share_service.py:41                → "공유 링크를 찾을 수 없거나 만료되었습니다."
```

받는 사람은 **자기 잘못인지, 링크가 낡은 건지, 앨범이 없어진 건지** 모른다.
보낸 사람도 "왜 안 열려?"라는 말을 듣고도 답할 말이 없다.

### ★ 먼저 확인해서 보고할 것

1. **지워진 앨범이 초대 링크로 열리는가?**
   `get_album_for_invite` 의 앨범 조회에 `deleted_at` 걸러내기가 **없다**
   (`select("*").eq("id", …)`). 지워진 앨범이 그대로 열리면 그것이 더 큰 결함이다.
   앨범을 지울 때 초대를 함께 껐다면 그 경로로 막히는 것인지 확인한다.
2. 네 가지 사정을 **지금 구분할 수 있는가?** `album_invites` 행에 남는 값
   (`is_active` · `expires_at` · `use_count` · 행 자체가 없음)으로 갈리는지 본다.
3. `share_links`(구경용)도 같은 구조인지 함께 본다.

### 고칠 것 — 사정마다 다른 말을 한다

★ **모든 경우에 "다음에 할 일"이 있어야 한다.** 막다른 골목을 만들지 않는다.

| 사정 | 문구 | 다음 행동 |
| --- | --- | --- |
| **앨범이 지워짐** | 이 앨범은 지워졌어요.<br>만든 분이 앨범을 지우면 링크도 함께 사라져요. | `내 앨범 만들기` |
| **기간이 지남** | 이 초대는 기간이 지났어요.<br>보내주신 분께 새 링크를 부탁해 보세요. | `내 앨범 만들기` |
| **참여가 끝남** | 이 앨범은 사진과 한마디를 다 모았어요.<br>보내주신 분께 물어보시면 다시 열 수 있어요. | `내 앨범 만들기` |
| **주소가 잘못됨** | 주소가 정확한지 확인해 주세요.<br>대화방의 링크를 다시 눌러 보시면 돼요. | `처음으로` |

- ★ **누구 잘못인지 말하지 않는다.** `잘못된 링크입니다` 처럼 받는 사람을 탓하지 않는다.
- ★ **기술 용어를 쓰지 않는다** — `토큰` · `만료` · `404` 는 화면에 나오지 않는다(§8).
  표의 `기간이 지났어요` 는 사용자 말이다.
- 문구는 **두 줄**이다. 첫 줄이 사실, 둘째 줄이 할 수 있는 일.
- 안내 껍데기(§9 — 배경 없음)를 쓴다. 이 화면은 오류가 아니라 **안내**다.
  받는 사람이 무엇을 잘못한 것이 아니다.
- ★ 브랜드 푸터는 남긴다. 이 사람이 이 서비스를 확인할 유일한 화면일 수 있다(§6).

### 구경용 링크(`/s/`)도 같다

같은 표를 쓴다. 문구에서 `초대` 를 `링크` 로만 바꾼다.

### 앨범을 지울 때 미리 알린다

지우기 확인 단계(§5)에 한 줄 더한다.

> 이미 보낸 링크도 함께 사라져요. 받은 분들은 더 이상 앨범을 볼 수 없어요.

- ★ **지우기 동작 자체는 바꾸지 않는다.** 한 줄 알려줄 뿐이다.
- 카카오톡 메시지는 지울 수 없으므로, **지우기 전에 아는 것**이 유일한 방법이다.

### 회귀 테스트

- ★ 네 가지 사정이 **서로 다른 문구**를 낼 것
- ★ 어느 경우에도 **다음 행동이 있을 것**(빈 화면으로 끝나지 않을 것)
- ★ 화면 문구에 `토큰` · `404` · `만료` 같은 기술 용어가 없을 것
- ★ **지워진 앨범이 링크로 열리지 않을 것**
- 지우기 확인 단계에 링크 안내가 있을 것
