## I-1. 🔴 사진은 기울었는데 흰 카드는 똑바로 서 있다 [완료 81f4e55]

화면에서 사진이 기울어도 **그 사진을 감싼 흰 카드는 그대로**다. 따로 논다.
스크랩북처럼 보이라고 넣은 기울기가 오히려 어긋나 보인다.

### 원인 (확인함)

기울기는 **안쪽 `figure`** 에 걸린다.

```
components/PhotoWithMemories.tsx:47
  const frameStyle = tilt !== 0 ? { transform: `rotate(${tilt}deg)` } : undefined;
  → <AlbumPhotoFrame style={frameStyle} …>   // figure.album-photo-frame
```

그런데 **화면에서 보이는 흰 카드는 그 figure 가 아니다.**

```
AlbumRenderer.css:80   .album-renderer--screen .album-screen-photo-card__frame {
                         border: 0; box-shadow: none; background: transparent; }   ← figure 는 투명
AlbumRenderer.css:56   .album-renderer--screen .album-screen-photo-grid > .photo-block {
                         border: 1px solid …; background: var(--c-surface);
                         box-shadow: var(--sh-md);
                         transform-origin: center center; }                        ← 이쪽이 흰 카드
```

`.photo-block` 에 `transform-origin` 까지 미리 적혀 있다. 돌릴 자리를 여기로 본 흔적인데
실제 `transform` 은 안쪽에 걸렸다.

### 고칠 것 — 카드를 돌린다. 단 글은 세운다

지금 `.photo-block` 안에는 **사진 + 캡션이 같이** 들어 있다. 그대로 돌리면 캡션도 기운다.
§9 는 `글은 똑바로`, CLAUDE.md §6 은 `캡션에 카드·테두리·그림자·배경색 금지`다.
**두 규칙이 같은 것을 가리킨다 — 흰 카드는 사진만 감싸야 한다.**

```
지금                          바꿀 것
┌─────────────┐             ┌─────────────┐   ← 이 카드가 기운다
│ ┌─────────┐ │             │   [사진]     │
│ │  사진    │ │  ← 기움     └─────────────┘
│ └─────────┘ │               캡션            ← 카드 밖, 똑바로, 배경 없음
│   캡션       │  ← 안 기움
└─────────────┘  ← 안 기움
```

- 흰 카드(테두리·배경·그림자)를 **사진을 감싸는 자리로** 옮기고, 기울기를 그 카드에 준다.
- 캡션은 카드 **밖 아래**에 둔다. 기울이지 않는다. 카드·테두리·그림자·배경색 없다.
- 기울기 값 자체(`scrapbookLayout`)는 그대로다. 값이 아니라 **걸리는 자리**만 바꾼다.
- 겹침(`--photo-overlap`)이 지금대로 동작하는지 확인한다. 카드 크기가 바뀌면 폭이 달라진다.
- ★ **인쇄는 건드리지 않는다.** 기울기가 인쇄에 새면 결함이다(§9).
  다만 인쇄에서도 캡션이 카드 밖으로 나가는 것은 I-4 와 맞물린다 — 함께 본다.

### 회귀 테스트

- 화면에서 **흰 카드와 사진의 각도가 같을 것** (지금은 카드 0도, 사진 n도)
- 캡션 각도가 0일 것
- 캡션에 배경·테두리·그림자가 없을 것
- 인쇄 렌더에 기울기 0건일 것 (기존 테스트 유지)

## I-2. 🔴 `공유하기` 가 화면마다 다른 것을 연다 [완료 42e9d82]

어디서는 시트가 뜨고 어디서는 카카오톡 대화방 선택창이 바로 뜬다.
**시트가 떠야 한다.** 무엇을 보내는지 고르지 않고 나가면 되돌릴 수 없다(§5).

### 원인 (확인함) — 진입점이 넷이고 서로 다른 것을 연다

| 자리 | 무엇을 여나 |
| --- | --- |
| `AlbumView.tsx:808` (앨범 상세) | **B-1 시트** ✅ |
| `AlbumResult.tsx:303·423` (**앨범 만든 직후**) | 옛 `share-modal` ❌ |
| `AlbumResult.tsx:287` `구경하라고 보내기` | 옛 `share-modal` ❌ |
| `CollaborationPanel.tsx:265` | **카카오 바로** ❌ |
| `PublicShareView.tsx:334` | **카카오 바로** ❌ |

B-1 에서 `AlbumView` 만 고쳤다. **가장 중요한 자리를 놓쳤다** — `AlbumResult` 는
앨범을 막 만든 직후 화면이고, 주최자가 태어나서 처음 공유하는 순간이 거기다.

§5 에 `진입점이 한 곳이어야 중복이 안 생긴다` 고 적어 둔 것이 지켜지지 않았다.
H-1 과 같은 종류다 — **한 행동에 자기 나름의 구현이 여럿**.

### 고칠 것

- **공유 시트를 공용 컴포넌트 하나로** 뽑는다(`AlbumShareSheet`). 지금 `AlbumView` 안에
  인라인으로 들어 있는 것을 꺼내는 것이다. 새로 만드는 것이 아니다.
- 위 네 자리가 **모두 그 하나를 연다.**
- 옛 `share-modal`(링크 복사 / 다른 앱으로 공유 / 카카오톡 공유)을 **없앤다.**
  그 세 버튼은 무엇을 보내는지 말하지 않는다 — B-1 이 고치려던 바로 그 문제다.
- 시트 구성은 §5 그대로: `함께 만들자고 보내기` / `구경하라고 보내기` / `링크 복사`,
  각각 설명 한 줄.
- ★ **주최자에게만 보인다.** H-1 에서 만든 `resolveAlbumRole` 로 판정한다.
  화면마다 다시 추측하지 않는다(§11).

### 회귀 테스트

- 네 자리 **어디서 눌러도 같은 시트**가 열릴 것
- 어느 자리도 카카오톡을 **바로** 열지 않을 것
- 옛 `share-modal` 이 코드에 남아 있지 않을 것
- 주최자가 아니면 어느 자리에도 없을 것

## I-3. PDF 를 누르고 나면 아무 표시가 없다 [완료 1d5120c]

`파일로 저장하기(PDF)` 를 누르면 **한참 아무 일도 일어나지 않다가**
브라우저·안드로이드의 다운로드 알림이 뜬다. 그게 첫 신호다.

### 원인 (확인함)

```
AlbumMoreSheet.tsx:64   onClick={() => { onClose(); onExportPdf(); }}
```

**시트를 먼저 닫는다.** 진행 표시(`PDF 만드는 중...`)는 그 시트 안의 버튼 라벨이라
같이 사라진다. 그 뒤로 완료까지 화면에 아무 변화가 없다.

### 고칠 것

- 시트를 닫아도 **앨범 화면에 진행 표시가 남는다.** 만드는 동안 계속 보인다.
- 끝나면 **우리 문구로** 알린다. 시스템 알림을 유일한 신호로 두지 않는다.
- 문구는 사용자 말로. 내부 사정을 말하지 않는다(§10).

  > 만드는 중 — `앨범을 파일로 만들고 있어요`
  > 끝났을 때 — `앨범 파일이 준비됐어요`

- ★ **가짜 진행률을 만들지 않는다**(F-3 과 같은 규칙). 몇 %인지 모르면 말하지 않는다.
- ★ 실패하면 실패라고 말한다. 조용히 끝나지 않는다(§11).
- 카카오톡 웹뷰에서 주소로 여는 경로(G-2)는 그대로다. 건드리지 않는다.

### 회귀 테스트

- 시트를 닫아도 진행 표시가 남을 것
- 끝났을 때 우리 문구가 뜰 것 / 실패했을 때 실패가 보일 것

## I-1b. 🔴 I-1 을 되돌린다 — 캡션은 프레임 안이다 [완료 aa0955c]

```
┌─────────────┐   ← 이 프레임이 통째로 기운다

│   캡션       │   ← 프레임 안
```

±3° 는 읽기에 지장이 없으므로 캡션도 프레임과 **함께 기운다.**

- ★ 기울기 값(`scrapbookLayout`)은 그대로. 인쇄 경로는 그대로.

## I-4. 🔴 열람용 PDF 손질 (§9)

실물 8쪽을 받아 한 장씩 봤다. 아래는 **본 것**이다.

### 4-1. 마지막 8쪽이 완전히 빈 페이지다

아무것도 없다. 지운다. **빈 페이지가 나오는 조건**을 찾아 막는다
(한 장 더 만들어 놓고 안 채운 것으로 보인다).

### 4-2. 표지 (1쪽)

- **사진이 아래에서 잘린다.** 페이지 밖으로 넘쳐 잘린 것이다.
  표지 사진은 **페이지 안에 온전히** 들어와야 한다.
- 표지 사진에만 프레임이 없다. 다른 쪽과 같은 프레임을 준다.
- 위쪽 절반이 비어 있다. 제목·날짜·사진을 페이지에 고르게 앉힌다.
- **`우리앨범` 로고가 작고 어둡다.** 표지에서 이 서비스를 알아볼 유일한 자리다.
  ★ 항상 **색이 들어간 `우리`+`앨범` 락업**으로, 표지에서는 **크게**(§9).
- 날짜 → **`2018년 11월 18일 ~ 20일`**. 년·월을 두 번 쓰지 않는다.

### 4-3. 날짜 머리글이 매 쪽 반복된다

지금 매 쪽 위에 이렇게 나온다.

```
        2018년 11월          ← 매번 같다. 필요 없다
   2018.11.18 (사진 1장)     ← 괄호도 필요 없다
```

- **`2018년 11월` 줄을 없앤다.** 표지에 이미 있다.
- **`(사진 N장)` 을 없앤다.** 세는 것은 앨범이 할 일이 아니다.
- 남는 것은 **날짜 하나**다 — `11월 18일`.
  해가 바뀌는 앨범이면 그 해 첫 날짜에만 `2018년`을 붙인다.

### 4-4. 가로 사진의 캡션이 멀리 떨어진다

5쪽이 가장 심하다. 가로 사진 한 장인데 **위아래로 크게 비고**, 캡션은 한참 아래
카드 바닥에 붙어 있다. 사진과 캡션이 남남으로 보인다.

- 카드 높이를 고정하지 않는다. **사진 크기에 맞춰 줄어든다.**
- 캡션은 **사진 바로 아래**다. I-1 의 "카드는 사진만 감싼다"와 같은 구조다.
- 한 장짜리 쪽이 페이지를 억지로 채우지 않는다. 남는 여백은 남겨 둔다.

### 4-5. 글자가 전반적으로 작다 — 값은 아래 표 그대로 쓴다

A4 로 인쇄해서 손에 들고 읽는 문서다. 화면 크기 감각으로 정하면 작다.

★ **재보지 않는다. 아래 값을 그대로 넣는다.** 크기 판단은 이미 끝났다.
기준은 A4 210×297mm, 96dpi 에서 **폭 794px = 210mm** 다.

| 자리 | pt | px (96dpi) |
| --- | ---: | ---: |
| 표지 — 앨범 이름 | 28 | **37** |
| 표지 — `우리앨범` 로고 | 17 | **23** |
| 표지 — 기간 | 12 | **16** |
| 날짜 머리글 | 13 | **17** |
| **캡션** | 11 | **15** |
| `YYYY.MM.DD의 이야기` 제목 | 12 | **16** |
| 날짜 이야기 본문 | 11 | **15** |
| `우리의 이야기` 제목 | 15 | **20** |
| `우리의 이야기` 본문 | 11.5 | **15** |
| `함께 만든 사람` | 10.5 | **14** |
| 브랜드 쪽 — 로고 | 22 | **29** |
| 브랜드 쪽 — 문구 | 12 | **16** |

- **본문 줄간격 1.6**, 제목 줄간격 1.3.
- 인쇄 루트의 실제 폭이 794px 이 아니면 **그 비율로 곱한다.**
  (예: 루트가 973px 이면 `× 973/794`.) 비율만 맞추고 재보지는 않는다.
- 값은 **인쇄 CSS 한 곳**에 변수로 둔다. 자리마다 숫자를 흩지 않는다.
- 사진이 가장 크다는 순서(§6)는 그대로다. 글이 사진을 이기면 안 된다.

### 4-6. 브랜드 쪽(7쪽)

- 위쪽 절반이 비어 있다. 내용을 페이지 가운데로.
- 로고가 작다. 이 쪽은 **브랜드를 보여주는 쪽**이라 크게.
- 문구 둘째 줄 앞에 공백이 하나 들어가 있다 — `  우리 가족의 앨범도…`. 정리한다.

### 지킬 것

- **A4 한 장에 사진 4장 이하**(§9). 지금 지켜지고 있다. 깨지 않는다.
- 사진은 자르지 않는다(`contain`).
- 인쇄용(200×200) 은 이번 범위가 아니다. **열람용만** 손댄다.
- ★ 화면(`AlbumRenderer` screen)을 건드리지 않는다. 인쇄 경로만이다.

### 회귀 테스트

- 마지막 쪽이 비어 있지 않을 것
- 표지 사진이 페이지 안에 온전히 들어올 것
- 한 쪽에 `(사진 N장)` · 중복된 `YYYY년 MM월` 이 없을 것
- 가로 사진과 캡션 사이 간격이 세로 사진과 같을 것
- 한 쪽에 사진 5장 이상이 오지 않을 것 (기존 테스트 유지)

## I-4b. 🔴 표본을 열어 보고 남은 것 (I-4 뒤)

사진을 줄이지 않는다 — 사진이 가장 중요하다(§6).

## I-4c. 🔴 4b-3 · 4b-4 를 철회한다 — 내 지시가 틀렸다

표본 9쪽을 다 열어 봤다. **표지와 브랜드 쪽은 이제 맞다**(프레임 있음, 로고 색 들어감).
나머지가 나빠졌고, 원인은 내가 4b 에서 준 두 지시다.

### ★ 철회 1 — "같은 줄에 있는 사진은 아래끝을 맞춘다"(4b-4)

**틀린 지시였다.** 이 말이 프레임을 격자 칸 높이까지 늘리는 구현으로 갔고,
가로 사진 아래에 **흰 카드만 절반이 남았다**(표본 2·4·5쪽). 폴라로이드가 아니라
빈 액자다. 그리고 6쪽에서는 사진이 프레임을 **뚫고 나와 서로 겹치고 날짜 머리글까지
덮었다** — 표본에서 가장 심하다.

**새 규칙 — 이것만 지킨다**

- ★ **프레임은 사진 크기다.** 사진 + 여백 4mm(+ 캡션). **절대 늘리지 않는다.**
  프레임이 사진보다 커지면 빈 액자가 된다. 격자 칸을 채우지 않아도 된다.
- ★ **사진은 절대 프레임 밖으로 나가지 않는다.** 지금 6쪽이 그렇다.
- 같은 줄의 사진은 **위끝을 맞춘다.** 아래끝은 비율에 따라 달라도 된다 —
  사진 크기가 다른데 아래끝을 맞추려 하면 반드시 빈 자리가 생긴다.
- 캡션은 사진 바로 아래 3mm. 그대로다.

### ★ 철회 2 — "쪽의 세로 가운데에 둔다"(4b-3)

**이것도 틀렸다.** 날짜 머리글까지 같이 내려가 **쪽 중간에서 시작한다**(표본 4쪽).
`우리의 이야기` 쪽도 여전히 아래 절반에 몰려 있다(8쪽).

**새 규칙**

- ★ **본문 쪽은 위에서부터 채운다.** 남는 여백은 **아래에 남긴다.** 책의 기본이다.
- ★ **날짜 머리글은 언제나 쪽 맨 위**다. 어떤 정렬에도 딸려 내려가지 않는다.
- 가운데 정렬은 **표지와 브랜드 쪽에만.** 그 둘은 지금 맞다. 건드리지 않는다.
- 4b-3 에서 맞았던 것 하나는 남긴다 — **좌우 기준선은 하나**(1장이든 2장이든
  같은 좌우 폭 안에서 시작).

### 4c-3. 이야기만 있는 쪽을 만들지 않는다

표본 3쪽·7쪽이 **글 세 줄만 있는 쪽**이다. 위 절반이 비고 종이만 쓴다.
4b-5(짧은 변 60mm)를 "3장부터 이야기를 넘긴다"로 옮긴 결과인데, 넘긴 결과가 더 나쁘다.

★ **새 규칙 — 날짜 이야기는 그 날의 마지막 사진과 같은 쪽에 둔다.**
자리가 모자라면 **이야기를 넘기지 말고 사진을 나눈다.**

- 4장 + 이야기가 안 들어가면 → **2장 / 2장 + 이야기**
- 3장 + 이야기가 안 들어가면 → **2장 / 1장 + 이야기**
- 사진 짧은 변 60mm 하한은 그대로다. 그 하한을 지키는 선에서 나눈다.
- **글만 있는 쪽은 만들지 않는다.** 단 `우리의 이야기`(앨범 끝 글)는 예외다 —
  그건 원래 자기 쪽을 갖는 글이다.

### 지킬 것

## I-4d. 🔴 프레임은 사진에 딱 붙는다 · 사진은 나란히 놓는다 [완료 d7501db]

표본을 다시 열어 봤다. **넘침·겹침·머리글 위치·글만 있는 쪽은 전부 잡혔다.**
남은 것 둘이고, 둘 다 내 표현이 나빠서 갈라진 것이다.

### 4d-1. 🔴 프레임 폭이 사진 폭과 다르다

세로로는 사진에 맞았는데 **가로로는 쪽 폭 전체**다. 사진은 그 안에 작게 가운데 놓이고
좌우로 흰 여백이 크게 남는다. **빈 액자가 방향만 바뀌었다.**

```
지금 (틀림)                        맞는 모양
┌───────────────────────┐         ┌─────────┐
│        ┌───────┐      │         │ [사진]   │   ← 프레임이 사진에 딱 붙는다
│        │ 사진   │      │         └─────────┘
│        └───────┘      │           캡션        ← 프레임 안, 사진 바로 아래
└───────────────────────┘
```

- ★ **프레임 폭 = 사진 폭 + 여백 4mm.** 세로와 똑같이 가로도 사진에 붙는다.
- ★ **프레임은 격자 칸을 채우지 않는다.** 칸 안에서 **가운데**에 놓인다.
- 남는 자리는 프레임 **밖**에 남는다. 프레임 안이 아니다.

### 4d-2. 🔴 사진이 세로로 한 줄씩 쌓인다 — 나란히 놓는다

★ **"좌우 기준선은 하나"(4b-3)를 철회한다.** 그건 정렬 이야기였는데
**칸을 하나로 줄이라는 말로 읽혔다.** 내 표현이 나빴다.

한 쪽의 사진 배치는 **장수로 정한다. 그림 그대로다.**

```
1장            2장                3장                4장
┌───────┐     ┌────┬────┐       ┌────┬────┐       ┌────┬────┐
│       │     │    │    │       │    │    │       │    │    │
│       │     │    │    │       ├────┴────┤       ├────┼────┤
└───────┘     └────┴────┘       │  가운데  │       │    │    │
                                └─────────┘       └────┴────┘
```

- ★ **세로로 쌓지 않는다.** 2장은 나란히, 4장은 2×2.
- 3장은 위에 둘, 아래 한 장을 가운데.
- 같은 줄의 프레임은 **위끝을 맞춘다**(4c 그대로). 아래끝은 달라도 된다.

### 4d-3. 4장 + 이야기를 먼저 한 쪽에 넣어 본다

2×2 로 돌아오면 4장 + 이야기가 한 쪽에 들어간다. 지금은 2장 / 2장으로 나뉘어
종이 두 장을 쓰고 사진도 작다.

- ★ **먼저 한 쪽에 넣어 보고, 사진 짧은 변이 60mm 미만이 될 때만 나눈다.**
- 나눌 때 규칙은 4c 그대로다(4장 → 2/2, 3장 → 2/1). 글만 있는 쪽은 만들지 않는다.

### 지킬 것

- ★ **재지 않는다.** 위 그림과 값이 전부다. 더 필요하면 물어본다.
- 표지 · 브랜드 쪽은 **맞다. 건드리지 않는다.**
- 4c 에서 잡은 것 — 넘침 없음 · 겹침 없음 · 머리글 맨 위 · 위에서부터 채움 ·
  글만 있는 쪽 없음 — **전부 그대로 지킨다.**
- 화면 렌더는 건드리지 않는다.

### 회귀 테스트

- ★ **프레임 폭이 사진 폭 + 여백과 같을 것** — 격자 칸 폭을 따라가지 않을 것
  (세로는 이미 잠겨 있다. 가로도 같은 방식으로 잠근다)
- ★ 한 쪽의 칸 수가 장수대로일 것 — **2장이 세로로 쌓이지 않을 것**
- ★ 4장 + 이야기가 60mm 를 지키면 한 쪽에 들어갈 것
- 4c 의 기존 항목 전부 유지

### 끝나면

표본을 다시 만들어 덮어쓴다. 내가 다시 연다.

## I-4e. 🔴 표본에 캡션이 한 글자도 안 나온다

I-4d 표본 7쪽을 다 열어 봤다. **배치는 이제 맞다** — 2×2 · 프레임이 사진에 붙음 ·
4장+이야기 한 쪽 · 넘침·겹침 없음 · 머리글 제자리. 여기는 건드리지 않는다.

그런데 **캡션이 한 글자도 안 보인다.** 표본 데이터에는 있다.

```
scripts/pdfSample.tsx:34              { shape: "가로", caption: "공항에서 내리자마자…" }
components/photoCaptionSegments.ts:22 add(photo.comment, photo.authorLabel);
```

표본은 `caption` 에 넣고 엔진은 **`photo.comment`** 를 읽는다. 이름이 어긋난다.
**G-1 에서 캡션이 조용히 죽었던 것과 같은 종류다**(§11 — 프런트와 서버가 주고받는
이름을 바꿀 때는 같은 커밋에서, 요청 본문을 확인하는 테스트와 함께).

### 먼저 확인해서 보고할 것

- ★ **실제 경로에서는 캡션이 PDF 에 찍히는가?**
  DB·API 의 `caption` 이 엔진의 `photo.comment` 로 옮겨지는 자리가 실제 경로에
  있는지 확인한다. 없으면 **사용자 앨범의 캡션이 PDF 에 안 찍힌다** — 그러면
  이것이 이번 큐에서 가장 큰 결함이다.
- 표본만의 문제라면 그렇게 보고한다.

### 고칠 것

- 표본 데이터가 **실제 경로와 같은 이름**을 쓰게 한다. 표본이 실물과 다르면
  표본으로 판단할 수 없다(4b-1 에서 같은 일이 있었다).
- 실제 경로에도 빠져 있었다면 그것을 고친다.
- ★ **엔진 안팎의 이름이 `caption` 하나로 통일될 수 있는지 함께 보고한다.**
  `comment` 는 §7 에서 폐기한 이름인데 엔진에 남아 있다. 고칠지는 보고를 보고 정한다.
  **이번에 임의로 바꾸지 않는다** — 넓게 퍼진 이름이다.

### 회귀 테스트

- ★ 캡션이 있는 사진은 **인쇄 렌더에 그 글자가 실제로 있을 것**
  (요소가 있는지가 아니라 **글자가 있는지**를 본다 — G-1 이 그래서 안 잡혔다)
- 캡션이 없는 사진에는 빈 자리가 생기지 않을 것
- 긴 캡션이 프레임 폭을 늘리지 않을 것 (4d 에서 잠근 것 유지)

### 끝나면

표본을 다시 만들어 덮어쓴다. **캡션이 눈에 보이는지** 내가 확인한다.

## I-4f. 브랜드 블록을 `우리의 이야기` 쪽 아래로 · 로고에 영문과 주소를 넣는다

### 4f-1. 브랜드 쪽을 따로 열지 않는다

지금은 브랜드가 **자기 쪽 하나**를 차지한다. 로고와 두 줄뿐인데 종이 한 장을 쓴다.

```
맞는 모양 — 들어가면 같은 쪽                     안 들어가면 다음 쪽
┌────────────────────┐                        ┌────────────────┐  ┌──────────────┐
│ 우리의 이야기        │                        │ 우리의 이야기    │  │              │
│ 본문 …              │                        │ 본문 …          │  │              │
│ 함께 만든 사람 — …   │                        │ 함께 만든 사람   │  │   [브랜드]    │  ← 지금과
│                     │                        │                │  │              │     같은 모양
│      [브랜드]        │  ← 쪽 아래에            └────────────────┘  └──────────────┘
└────────────────────┘
```

- ★ **먼저 `우리의 이야기` 쪽 아래에 넣어 본다.** 들어가면 거기서 끝난다.
- ★ **자리가 모자라면 다음 쪽에 지금과 똑같은 모양으로** 낸다(쪽 가운데).
  지금 브랜드 쪽은 맞다 — 그 모양을 바꾸지 않는다.
- 같은 쪽에 올 때는 **쪽 아래에 붙인다.** 본문 바로 뒤에 붙이지 않는다.
  `우리의 이야기`와 `함께 만든 사람`은 위에서부터 채운 자리 그대로다(4c).
- 판정 기준은 **자리가 있느냐 하나**다. 넘치면 다음 쪽, 그것뿐이다.

### 4f-2. 로고 아래에 영문과 주소

```
        ♥ 우리앨범          ← 지금 있는 락업 (우리=진한 글자색 / 앨범=브랜드색)
        woorialbum         ← 새로. 영문
      www.woorialbum.com   ← 새로. 주소
```

- 순서는 **로고 → 영문 → 주소**다.
- 크기 — 영문 **12px** · 주소 **12px**. 로고(29px)보다 작다.
- 색 — 영문·주소 모두 **본문 보조색**(로고 색을 쓰지 않는다. 로고가 주인공이다).
- 줄간격 1.5. 셋 다 가운데 정렬.
- ★ **문자열은 `lib/brand.ts` 한 곳에서 읽는다.** 화면·PDF가 같은 값을 본다(§3).
  주소가 바뀔 때 고칠 자리가 하나여야 한다.
- 주소는 **글자로만** 쓴다. 링크로 만들지 않는다 — 인쇄물이다.

### 지킬 것

- 4c·4d 에서 잡은 것 전부 그대로. 표지도 그대로.
- ★ 재지 않는다. 위 값이 전부다.

### 회귀 테스트

- ★ 자리가 있으면 브랜드가 `우리의 이야기`와 **같은 쪽**에 있을 것
- ★ 자리가 없으면 **다음 쪽에 지금 모양 그대로** 있을 것
- 로고 아래에 영문과 주소가 그 순서로 있을 것
- 문자열이 `lib/brand.ts` 한 곳에서 나올 것

## I-4g. 🔴 인쇄에서 캡션을 자르지 않는다 [완료 299e271 f8a5fc1]

캡션이 이제 보인다(4e). 그런데 **잘린다.**

```
표본 데이터   숙소 앞 돌담. 여기서 한참 서 있었다. 아무도 먼저 들어가자는 말을 안 했다.
찍힌 것       숙소 앞 돌담. 여기서 한참
              서 있었다. 아무도 먼저          ← 끊김. `…` 도 없다
```

**화면의 2줄 제한이 인쇄까지 따라왔다.** 화면은 사진을 크게 보이려고 자르는 것이
맞지만(§6), **인쇄는 자를 이유가 없다.** 캡션은 인쇄까지 가는 유일한 글이다.
문장이 중간에 끊기면 그 사람이 남긴 말이 반쪽만 남는다.

### 고칠 것

- ★ **인쇄에서는 줄 수 제한을 없앤다.** 캡션 전체를 보여준다.
  화면의 2줄 + `…` 는 그대로 둔다.
- 캡션이 길어져 프레임이 세로로 길어지면 **사진 상한을 그만큼 줄여** 쪽에 맞춘다.
  ★ 넘치게 두지 않는다(4c 에서 잡은 것). 잘리는 것보다 사진이 조금 작은 편이 낫다.
- ★ 캡션이 프레임 폭을 늘리지 않는 것은 그대로다(4d).
- 아주 긴 캡션(예: 300자)이 와도 쪽이 깨지지 않아야 한다. 그때는 **그 사진만
  다음 쪽으로** 보낸다 — 4c 의 "사진을 나눈다"와 같은 방식이다.

### 회귀 테스트

- ★ 인쇄 렌더의 캡션 글자가 **원문과 같을 것**(잘린 문자열이 아닐 것)
- ★ 인쇄 CSS 에 줄 수 제한(`-webkit-line-clamp` · `max-height` 등)이 없을 것
- 화면 렌더는 여전히 2줄 + `…` 일 것
- 긴 캡션이 와도 쪽이 넘치지 않을 것 / 프레임 폭이 늘지 않을 것

### 끝나면

표본을 다시 만든다. **긴 캡션 하나를 데이터에 넣어** 잘리지 않는 것을 볼 수 있게 한다.

## I-5. 오류·안내 블록을 한 종류로

같은 성격의 알림인데 화면마다 생김새가 다르다. 어떤 것은 스크린리더에 읽히고
어떤 것은 안 읽힌다. 사용자가 느끼는 "제각각" 의 남은 원인이다.

### 먼저 조사해서 보고할 것 — 보고 후 멈춘다

- **오류·안내를 그리는 자리를 전부 찾는다.** 목록이 아니라 규칙으로 찾는다:
  `role="alert"` · `role="status"` · `__error` · `__notice` · `__hint` · `__warning`
  같은 이름을 쓰는 모든 자리.
- 각각에 대해 표로 낸다 — **어느 화면 / 성격(오류·주의·안내·성공) / 역할 속성 /
  색·배경·아이콘 / 사라지는가**.
- ★ **몇 종류가 필요한지는 그 표를 보고 정한다.** 지금 12종이라도 실제 성격은
  서너 가지일 수 있다. 미리 개수를 정하지 않는다.

### 고칠 때

- 성격별로 **하나의 껍데기**를 만든다. 정의는 한 곳(CSS 한 파일).
- ★ **오류는 `role="alert"`, 진행·성공은 `role="status"`.** 지금 빠진 자리가 있다.
- ★ **색만으로 성격을 구분하지 않는다.** 40~60대에 색약이 흔하다.
  글머리 표시나 아이콘이 함께 있어야 한다.
- 문구는 건드리지 않는다. **생김새와 읽힘만** 통일한다.
- 화면 배치·위치는 그대로. 이번에 옮기지 않는다.

**회귀 테스트** — 정의가 한 곳일 것 / 오류 자리에 `role="alert"` 이 빠진 곳이 없을 것 /
성격이 색 말고도 구분될 것

## I-6. 로딩 표시를 한 종류로

로딩 shimmer 가 화면마다 방향·속도가 달라 눈에 띈다.

- I-5 와 같은 방식이다. **먼저 찾아 표로 내고 보고한 뒤 멈춘다.**
- 통일할 때 **정의는 한 곳**이다. 방향·속도·색을 화면 CSS 에 적지 않는다.
- ★ `prefers-reduced-motion` 을 존중한다. 끄면 움직이지 않는 자리표시자만 남는다.
- ★ **로딩이 0.3초 안에 끝나는 자리에는 shimmer 를 넣지 않는다.** 깜빡임이 더 나쁘다.

**회귀 테스트** — 정의가 한 곳일 것 / 방향·속도가 화면마다 다르지 않을 것

## I-7. 앨범 만들 때 고르는 분류를 다섯 개로

지금 일곱 개다 — `가족 · 친구 · 연인 · 동료 · 반려동물 · 여행 · 기타`.

- **`반려동물`을 없앤다.** 사람들은 반려동물을 가족으로 여긴다. 따로 두면
  "우리 강아지는 가족이 아닌가" 하고 한 번 멈춘다.
- **`여행`을 없앤다.** 나머지는 **누구와** 만든 앨범인지인데 여행만 **무엇을** 했는지다.
  기준이 섞여 있어 가족과 간 여행은 어디에 넣을지 알 수 없다.
- 남는 다섯 개 — **`가족 · 친구 · 연인 · 동료 · 기타`**

### ★ PO 판단 (2026-08-09)

- 분류는 **만들 때만 고른다. `내 앨범` 화면에는 나오지 않는다.**
  표지 느낌과 이야기 문체에만 쓴다. 앨범이 1~3개인 사람에게 거를 것이 없다.
- `내 앨범`은 **세 칸 그대로**다(§1). 합치지 않는다.

### 이미 `pet` · `travel` 로 저장된 앨범이 있다

★ **데이터를 지우거나 바꾸지 않는다.** 그 사람의 앨범이다.

- 저장된 값은 그대로 읽는다. 문체·표지 규칙도 그대로 남긴다
  (`album_styles.py` · `story_service.py` 의 `pet` · `travel` 항목).
- **고르는 목록에서만 뺀다.** 앞으로 새로 선택되지 않을 뿐이다.
- 백엔드 `AlbumCategory` 타입에서도 빼지 않는다. 빼면 기존 앨범을 읽다 막힌다.
- 먼저 프로덕션에 `pet` · `travel` 앨범이 몇 건인지 세어 **보고에 적는다.**

### 고칠 것

- `frontend/src/types.ts` 의 `ALBUM_CATEGORY_OPTIONS` 에서 두 줄을 뺀다.
- 그 목록을 읽어 그리는 화면은 그대로다. **화면 코드를 건드리지 않는다.**
- 다섯 개가 한 줄에 안 들어가면 줄바꿈은 지금 방식 그대로 둔다.

**회귀 테스트** — 고르는 목록이 다섯 개일 것 / `pet` · `travel` 로 저장된 앨범이
여전히 열리고 문체 규칙이 적용될 것
