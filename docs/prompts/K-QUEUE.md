## ★ PO 판단 (2026-08-09) — 담아두기 403

### 답: **담아두기는 구경꾼의 행동이 맞다**

## K-7c. 🔴 로그인한 구경꾼이 화면에 갇힌다 [완료 f6ee4ee] — **크기: 보통**

**근거: SCREEN_SPEC 22차 §3 · §5** (2026-08-09 개정). 문서를 먼저 읽고 시작한다.

### 실기기에서 본 것 (2026-08-09, 노트20)

공유 링크(`/s/<token>`)로 들어와 **담아두기 → 로그인까지 끝낸 상태**인데,

1. 헤더 오른쪽에 **`⋯` 하나뿐**이다. `내 앨범` 이 없다.
   구경꾼 하단 네비는 `내 앨범 만들기` 1칸이라 **돌아갈 길이 아예 없다.**
2. `⋯` 를 열면 **이메일 줄 아래로 아무것도 없다.** 로그아웃도 회원 탈퇴도 없다.

즉 **로그인은 됐는데 나갈 수도 로그아웃할 수도 없다.** 앱을 닫는 것 말고 방법이 없다.

### 원인 (★ 짐작이다 — 코드에서 확인하고 시작한다)

두 화면 모두 **역할(구경꾼)만 보고** 그렸을 것이다.
`구경꾼 = 비로그인` 이 오래 참이었기 때문에 그렇게 써도 문제가 없었다.
F-1(담아두기)이 **로그인한 구경꾼**을 만들면서 그 전제가 깨졌다.

### 고칠 것 — 두 곳

**(1) 헤더 — 로그인 상태면 `내 앨범` 을 보여준다**

```
공유 앨범 화면(/s/<token>) 헤더 오른쪽

비로그인 :  [ 로그인 ]
로그인   :  [ 내 앨범 ]  [ ⋯ ]
```

- 판단 기준은 **역할이 아니라 로그인 여부**다.
- 같은 규칙이 **참여하기 화면에 이미 들어가 있다.** 그 코드를 찾아 **그대로 쓴다.**
  새로 만들지 않는다. (§13 — 공통 함수가 있으면 재사용한다)

**(2) `⋯` 시트 — 로그인 상태면 계정 · 로그아웃 · 회원 탈퇴가 보인다**

| 항목 | 비로그인 구경꾼 | **로그인한 구경꾼** |
| --- | --- | --- |
| 계정 (이름 · 이메일) | `로그인` 버튼 | **보인다** |
| 로그아웃 | — | **보인다** |
| 회원 탈퇴 | — | **보인다** |
| 표지 사진 · PDF · 함께한 사람 · 새 앨범 · 앨범 지우기 | — | — (그대로 없다) |

- 구경꾼이 얻는 것은 **자기 계정을 다루는 줄 셋뿐**이다.
  앨범에 대한 권한은 **하나도 늘지 않는다.** 늘리면 안 된다.
- 시트가 세 줄뿐이라 비어 보이면 안 된다. 위 여백을 §7 규칙대로 준다.

### 하지 말 것

- **주최자·참여자 시트를 건드리지 않는다.** 구경꾼 분기 하나만 는다.
- **역할 판정 코드를 손보지 않는다.** `resolveAlbumRole`(H-1) 은 그대로다.
  이번 건은 역할이 아니라 **로그인 여부**를 안 본 것이다.
- 전수 조사를 하지 않는다. 위 두 화면만 본다.

### 확인 (BJ 가 실기기로 한다 — 코드는 화면만 맞춰 놓는다)

```
로그아웃 상태로 공유 링크 열기 → 헤더에 [로그인] 하나
담아두기 → 로그인 → 돌아온 화면
   → 헤더에 [내 앨범] [⋯] 둘
   → ⋯ 열면 이메일 · 로그아웃 · 회원 탈퇴 셋
   → 내 앨범 누르면 내 앨범으로 간다
```

### ★ 이번에 배운 것 (SCREEN_SPEC 22차에 넣었다)

> **새 상태를 만들면 그 상태가 지나가는 모든 표를 다시 본다.**
> F-1 을 넣을 때 §3·§5 의 역할 칸을 다시 안 봐서 갇히는 사람이 생겼다.

## K-8. 할 일이 있는 결과는 눈에 띄어야 한다 — **크기: 보통**

PDF 를 받지 못했을 때 뜨는 안내가 **화면 맨 아래에 지나가듯 떠서 눈에 안 띈다.**
그런데 그 안내는 **사용자가 뭔가를 해야** 파일을 받을 수 있는 내용이다.

I-3 에서 PDF 표시를 하단 고정으로 둔 것은 **만드는 동안 화면을 가리지 않으려고**였다.
그건 맞았다. 문제는 **끝났고 사용자가 할 일이 있는 경우**까지 같은 자리에 둔 것이다.

### 자리 — 셋으로 나눈다

| 상태 | 자리 |
| --- | --- |
| **만드는 중** | 하단 고정 · 가리지 않음 **(지금 그대로)** |
| **끝났고 할 일 없음** | 하단 고정 · 사용자가 닫음 **(지금 그대로)** |
| **끝났는데 할 일이 있음** | ★ **화면 가운데 시트 + 딤** |

- ★ 딤과 시트는 **이미 있는 것을 쓴다** — `album-sheet-dim` · `album-inline-action`.
  새로 만들지 않는다(§11).
- 사용자가 방금 누른 행동의 결과다. **가려도 된다.** 놓치면 무엇을 해야 할지 모른다.
- 버튼은 **`확인` 하나.** 되돌릴 것이 없다.

### 문구 — 다시 쓴다

```
지금
  카카오톡 안에서는 파일 저장이 막혀 있어요. 메뉴(⋯)에서 '다른 브라우저로 열기'를
  눌러 크롬이나 사파리에서 저장해 주세요.
```

문제 셋 — `막혀 있어요`로 **나쁜 소식부터** 말하고, **어디를 눌러야 하는지** 없고,
`크롬이나 사파리`라는 이름을 대서 **그게 뭔지 찾게** 만든다.

```
바꿀 것

  앨범 파일이 준비됐어요                       ← 제목. 굵게

  카카오톡에서는 바로 저장되지 않아요.
  브라우저 메뉴(⋮ 또는 ···)에서
  '다른 브라우저로 열기'를 고르면 저장할 수 있어요.

                                    [ 확인 ]
```

- ★ **좋은 소식이 먼저다.** 파일은 실제로 만들어져 있다. 그것부터 말한다.
- ★ **`크롬`·`사파리`를 빼낸다.** `다른 브라우저로 열기`를 고르면 알아서 열린다.
  이름을 대면 40~60대는 그것을 찾아 헤맨다.
- ★ 아이콘을 **둘 다** 보여준다(`⋮` · `···`). 기기·버전마다 다르다.
- `막혀 있어요` → `바로 저장되지 않아요`. 사실은 같고 누구 탓도 아니다.

### 색

- 오류가 아니라 **안내**다. 사용자가 잘못한 것이 없다 — danger 색을 쓰지 않는다(I-5b).
- 눈에 띄는 것은 **색이 아니라 자리와 딤**이 맡는다.
- 제목만 굵게. 본문은 지금 크기.

### 지킬 것

- ★ **만드는 중 표시와 성공 표시는 건드리지 않는다**(I-3). 자리도 그대로다.
- ★ 이 안내는 **K-6 이 고쳐지면 거의 안 뜬다.** 그래도 마지막 안내라 좋아야 한다.
  네트워크가 나쁘면 언제든 이 길로 온다.

### 회귀 테스트

- ★ 할 일이 있는 결과가 **딤 위 시트**로 뜰 것
- ★ 만드는 중 표시는 여전히 **하단 고정**일 것
- 문구에 `크롬` · `사파리` · `막혀` 가 없을 것

### 겸사겸사 — 같은 행동에 두 가지 말 (PO 판단 2026-08-09)

지금 같은 행동(카카오 로그인)에 말이 둘이다.

```
JoinPage.tsx:181   카카오로 시작하기     ← 초대장 화면의 큰 버튼
AuthPanel.tsx:33   카카오로 계속하기     ← 로그인 대화상자
```

**둘 다 `카카오로 계속하기` 로 맞춘다.**

- `시작하기` 는 **처음 오는 사람에게만** 맞는 말이다. 이미 회원인 사람에게는
  **가입처럼 읽힌다** — PO 가 실기기에서 실제로 그렇게 느꼈다.
  *"솔직히 계속 회원가입하는 꼴이잖아"* (2026-08-09).
- `계속하기` 는 처음 오는 사람에게도 맞고 돌아온 사람에게도 맞다.
- 이 두 곳만 본다. 전수 조사를 하지 않는다.

## K-2. 🔴 FK 를 `CASCADE` 로 — **크기: 큼**

`albums` 를 가리키는 자식 17개 중 **8개가 `RESTRICT`** 이고 의존이 **두 겹**이다.

```
memory_answers → memory_questions → album_media → albums
guest_memory_submissions → share_links → albums
```

그래서 삭제 RPC 가 **순서를 손으로 알고 있어야 한다.**
2026-08-09 에 PO 가 앨범을 지우려다 두 번 막혔고, 나(문서 쪽)도 순서를 두 번 틀렸다.

★ **DB 가 알려주지 않으면 사람은 반드시 틀린다.**
새 자식 테이블이 하나 얹히고 RPC 에 안 들어가면, **그 순간부터 프로덕션에서
앨범 삭제가 조용히 실패한다.** 테스트로도 안 잡힌다.

### 고칠 것

- `albums` 를 가리키는 `RESTRICT` 여덟을 **`ON DELETE CASCADE`** 로.
  `album_media` · `album_members` · `album_photos` · `album_story_inputs` ·
  `guest_album_sessions` · `guest_memory_submissions` · `memory_questions` · `share_links`
- 자식들끼리의 `RESTRICT` 도 같이 — `memory_answers → memory_questions`,
  `memory_questions → album_media`, `guest_memory_submissions → share_links`,
  `photo_memories → album_contributors`
- ★ **`SET NULL` 은 그대로 둔다** — `analytics_events` · `ai_usage_logs`.
  통계는 앨범이 사라져도 남아야 한다.
- ★ **RPC 의 손 열거를 지운다.** DB 가 하는 일을 코드가 또 하지 않는다.

### ★ 확인해서 보고할 것

- 지금 RPC(`delete_album_cascade`)가 위 여덟을 **다 지우는가?** 하나라도 빠져 있으면
  그것이 이미 결함이다.
- CASCADE 로 바꾼 뒤 **RPC 가 하는 일이 남아 있는가?** 없으면 RPC 를 지울지 보고한다.
  (권한 검사는 API 가 이미 한다)

### 회귀 테스트

- ★ 앨범 하나를 지우면 **자식이 전부 사라질 것** — 여덟 테이블 모두
- ★ `analytics_events` · `ai_usage_logs` 는 **남고 `album_id` 만 비워질 것**
- ★ 코드에 삭제 순서를 손으로 적은 곳이 없을 것

## K-9. 🔴🔴 게스트 앨범 `저장하기` 가 앨범을 잃게 한다 — **크기: 큼 · 이 큐에서 제일 먼저**

★ **이것은 데이터를 잃는 결함이다.** CLAUDE.md §9 — *사용자 데이터는 절대 잃어버리면 안 된다.*

### 프로덕션 실측 (2026-08-09, 내가 Supabase 에서 직접 확인)

BJ 가 게스트로 앨범을 만들고 `저장하기 → 카카오 로그인` 을 **세 번** 했다.
결과 화면: `앨범을 찾을 수 없어요 / You do not have permission to view this album.`

```
public.albums  (게스트 앨범 3건, 13:31 · 13:33 · 13:37)
  owner_id    = NULL   ← 세 건 전부
  created_by  = NULL   ← 세 건 전부
  status      = active  (앨범 자체는 살아 있다)

public.album_contributors / album_members
  이 세 앨범에 대한 행 0건

public.guest_album_sessions  (3건, 앨범과 1:1)
  status            = 'active'
  claimed_profile_id = NULL   ← 세 건 전부
  claimed_at         = NULL   ← 세 건 전부
```

### 이것이 말해주는 것

- **가져오기(claim) 장치는 이미 있다.** `guest_album_sessions.claimed_profile_id` ·
  `claimed_at` 이 그것이다. 새로 설계할 것이 아니다.
- **그런데 한 번도 실행되지 않았다.** 세 번 다 `NULL` 이다.
- 그래서 로그인 뒤 돌아온 화면이 `/album/{id}` 였고, 그 계정은 멤버가 아니라 **403**.
- ★ **담아두기(K-7)와 완전히 같은 모양이다** — 로그인은 되는데 **그 다음 문에서 막힌다.**
  로그인 성공을 일의 완료로 착각한 자리가 또 있는 것이다.

### 갈라야 할 것 — 셋 중 어디서 끊겼나

로그로 확인한다. 짐작하지 말고 어디까지 갔는지 본다.

```
① 로그인 전 : 저장하겠다는 의도(게스트 토큰 포함)를 어딘가에 남기는가?
② 로그인 후 : 돌아와서 claim API 를 실제로 부르는가?  (네트워크 로그)
③ 서버      : claim 이 owner_id 를 채우고 세션을 claimed 로 바꾸는가?
```

`claimed_profile_id` 가 `NULL` 이므로 **③까지 간 적은 없다.** ①이나 ②다.
K-7 [1/3](d4e30c6)에서 "하려던 일을 기억한다"를 담아두기에만 붙였다면 **여기가 그 나머지**다.

### 반드시 지킬 것

- **claim 이 끝나면 `albums.owner_id` 를 채운다.** SCREEN_SPEC §1 —
  *소유권은 `albums.owner_id` 하나로 판정한다.* `album_members` 행만 넣고 끝내면
  `내 앨범` 에 안 뜬다.
- `created_by` 도 함께 채운다(기록용). 판정에는 쓰지 않는다.
- `guest_album_sessions` 를 `claimed_profile_id` · `claimed_at` · `status` 로 닫는다.
  **닫지 않으면 만료 정리가 남의 앨범을 지운다.**
- **한 번만 가져올 수 있게 한다.** 이미 `claimed` 인 세션에 다른 계정이 claim 하면 거절한다.
- **실패하면 말한다**(§11). 지금은 아무 말 없이 403 화면으로 떨어진다.
- 돌아오는 자리는 **`/album/{id}`** 가 맞다. claim 이 성공했으면 그 문이 열린다.
  claim 을 건너뛰고 문만 여는 식으로 우회하지 않는다.

### 지금 살아 있는 세 앨범

지우지 않는다. 고친 뒤 **같은 기기에서 다시 `저장하기`** 를 눌러 살아나는지 본다.
(게스트 토큰이 그 폰에 남아 있으면 살아난다. 안 되면 내가 SQL 로 붙여준다.)

### 겸사겸사 확인만 (고치지 말 것)

`guest_album_sessions.expires_at` 이 **생성 +7일**이다. SCREEN_SPEC §1 은 **14일**이라고
적혀 있다. **지금 바꾸지 않는다** — J-15 에서 한 번에 정한다. 여기서는 보고만 한다.

## K-10. 사진 고르기 화면에서 앞쪽 미리보기가 깨진다 — **크기: 보통**

### 실기기 (2026-08-09, 노트20 · 카카오톡 웹뷰 · 3회 재현)

사진 3장을 고르면 **1번(때로는 2번까지) 미리보기가 빈 분홍 박스**가 되고
깨진 이미지 아이콘과 `선택한 사진 1` 이라는 대체 텍스트가 보인다. **3번은 정상.**
그 상태로 앨범을 만들면 **앨범에서는 세 장 다 멀쩡히 보인다.**

즉 **파일은 멀쩡하고 미리보기 주소만 죽었다.**

### 원인 (★ 짐작이다 — 코드에서 확인하고 시작한다)

`URL.createObjectURL` 로 만든 주소가 **아직 화면에 쓰이는 중에 `revokeObjectURL` 된다**고 본다.
앞쪽 것부터 죽고 마지막 것만 사는 모양이 그 패턴이다.
사진을 더 고를 때마다 도는 정리(useEffect cleanup 등)가 **이전 주소를 전부 거둬가는데
다시 만들지는 않는** 자리를 찾는다.

### 고칠 것

- 미리보기 주소는 **그 사진이 목록에서 빠질 때와 화면을 떠날 때에만** 거둔다.
  목록이 바뀔 때마다 전부 거두지 않는다.
- 주소를 **사진 한 장에 하나로 묶어** 들고 있는다. 목록을 다시 그릴 때 새로 만들지 않는다.
- ★ **깨진 미리보기를 사용자에게 보이지 않는다.** 주소가 죽었으면 대체 텍스트 대신
  회색 자리를 둔다. `선택한 사진 1` 같은 개발용 문구가 화면에 나오면 안 된다(§8).

### 하지 말 것

- 업로드·압축·리사이즈 경로를 건드리지 않는다. 그쪽은 정상 동작 중이다.
- 사진 고르기 화면을 다시 만들지 않는다. 주소 수명만 고친다.

## K-11. 오류 화면에 영어가 그대로 나온다 — **크기: 작음 · K-8 과 같이 한다**

실기기에서 본 화면:

```
  앨범을 찾을 수 없어요
  You do not have permission to view this album.      ← 서버 원문이 그대로
  [ 다시 시도 ]  [ 새 앨범 만들기 ]                     ← 진한 빨강 두 개
  (하단에 사진 추가 · 한마디 쓰기 · 공유하기 가 그대로 있다)
```

- **영어 원문을 사용자에게 보이지 않는다**(§8). 서버 메시지는 기록에만 남기고,
  화면에는 우리 말로 쓴 문구를 낸다.
- **제목과 설명이 서로 다른 말을 한다.** `찾을 수 없어요`(없다)와 `permission`(있는데 못 본다)이
  같이 있다. 하나로 정한다.
- **못 여는 앨범 화면의 하단 네비에 `사진 추가` · `한마디 쓰기` · `공유하기` 를 두지 않는다.**
  열지도 못하는 앨범에 사진을 더하라고 권하는 꼴이다.
- 버튼 색은 K-8 에서 정하는 것을 따른다. 여기서 따로 정하지 않는다.

## K-12. 담아둔 뒤에도 `담아둘까요?` 가 그대로 남는다 — **크기: 보통**

**근거: SCREEN_SPEC 25차 §1.** 문서를 먼저 읽고 시작한다.

### 실기기 (2026-08-09, f6ee4ee 배포 뒤)

공유 링크 → `담아두기` → 카카오 로그인 → 돌아옴.
**담기는 성공했다** (내가 프로덕션에서 확인 — `album_bookmarks` 1행,

### 고칠 것

**(1) 담긴 뒤에는 같은 자리가 담긴 상태로 바뀐다**

```
안 담김 :  이 앨범을 내 앨범에 담아둘까요?

```

- 담긴 뒤 자리에 **`빼기` 를 두지 않는다.** 빼는 자리는 `내 앨범` 의 담아둔 목록 하나다.
  담자마자 뺄 일은 없고, 버튼이 둘이면 무엇을 누를지 생각해야 한다.
- `내 앨범에서 보기` 는 헤더의 `내 앨범` 과 **같은 곳으로 간다.** K-7c 에서 쓴 것을 재사용한다.

**(2) 다시 들어와도 담긴 상태로 보인다**

지금은 화면을 새로 열면 다시 물을 것이다(담긴 걸 모르니까).

- 공유 화면 응답에 **`이 사람이 이 앨범을 담아뒀는가`** 를 싣는다.
- **새 API 를 만들지 않는다. 기존 공유 응답을 넓힌다**(§10).
- 로그인했을 때만 의미가 있다. 비로그인이면 늘 `안 담김` 이다.

### 하지 말 것

- 담아두기 API 를 손대지 않는다. **동작한다** — 프로덕션에서 확인했다.
- `내 앨범` 의 담아둔 앨범 목록을 손대지 않는다. 이번 건은 공유 화면 하나다.
- K-7c 에서 만든 헤더·시트를 손대지 않는다.

### ★ 이번에 배운 것 (SCREEN_SPEC 25차)

> **일이 끝났으면 화면이 그 사실을 말해야 한다.**
> K-7 · K-9 는 끝났는데 **말이 없어서** 났고, 이번엔 끝났는데 **묻는 말이 그대로 남아** 났다.

- ★ **미리 체크된 상태로 보여주지 않는다.** 켜져 있는 동의는 동의가 아니다.
  보이면 반드시 사용자가 직접 켠다. 안 보이거나, 비어 있거나 둘 중 하나다.

### 하지 말 것

- **로그인보다 앞에 있는 동의 순서를 뒤집지 않는다.** 지금 순서를 그대로 둔다.
  (개인정보를 받기 전에 동의를 받는 순서가 안전하다.)
- **묵시적 고지로 되돌리지 않는다.** `계속하면 동의한 것으로 봅니다` 는
  일부러 체크로 바꾼 것이다(그 이유가 `LegalConsent.tsx` 주석에 있다).
- 동의 기록용 **새 테이블을 만들지 않는다.** `profiles` 두 칸이면 된다.
- `LegalConsent` 를 **두 벌로 만들지 않는다.** 로그인 모달과 게스트 저장이 같이 쓴다.

### 반드시

- Migration 과 rollback 을 같이 낸다.
- 기존 회원은 `legal_agreed_at` 이 비어 있다 — **다음 로그인 때 한 번 받는다.**
  기존 회원을 임의로 "동의한 것"으로 채우지 않는다. 그건 기록이 아니라 조작이다.
- 정책을 뒤집었으므로 `LegalConsent.tsx` 의 주석
  (*"체크 상태를 저장하지 않는다"*)을 **같은 커밋에서** 고친다(§11).

### 남길 질문 (코드가 판단하지 않는다 — 보고만 한다)

`카카오로 시작하기` 문구가 이미 회원인 사람에게 가입처럼 읽힌다. K-8 에서 정한다.

## K-17. 🔴 회원 탈퇴가 지금은 막힌다 — **크기: 큼**

★ **되돌릴 수 없는 일이다. 사용자 데이터를 지운다. 천천히, 정확하게 한다.**

### 지금

`회원 탈퇴` 는 §5 에 살아 있는 버튼인데, **앨범이 있는 사람은 실패한다.**
`profiles` 를 가리키는 FK 넷이 `RESTRICT` 다(2026-08-10 프로덕션 확인).

```
albums.created_by · album_members.profile_id
family_members.profile_id · family_invitations.inviter_id
```

반대로 **이미 알아서 끊기게 되어 있는 것**도 있다 — 이쪽은 손대지 않는다.

```
album_photos.contributor_profile_id     SET NULL   ← 남의 앨범에 올린 사진
album_story_inputs.author_profile_id    SET NULL   ← 내가 쓴 한 줄·이야기
album_contributors.user_id              SET NULL
album_bookmarks.user_id                 CASCADE    ← 담아둔 목록은 사라진다
```

### 정한 것 (PO 판단 2026-08-10)

```
내가 만든 앨범           →  앨범 · 사진 · 파일까지 전부 지운다
남의 앨범에 남긴 사진·한 줄  →  그대로 두고 이름만 지운다
```

★ **남의 앨범을 깨뜨리지 않는다.** 그 앨범은 다른 사람의 추억이고 그 사람은 잘못이 없다.
개인정보(이름·계정 연결)는 확실히 끊고, 사진은 그 앨범의 것으로 남긴다.

★ **숨기지 않는다.** 탈퇴 화면에 두 갈래를 다 적는다. 아래 문구 그대로 쓴다.

### 화면 — 확인 시트

숫자는 **실제로 세어서** 넣는다. `000개` 같은 빈칸을 두지 않는다.

```
정말 탈퇴하시겠어요?

  내가 만든 앨범 3개 · 사진 47장
  탈퇴하면 앨범과 사진이 모두 지워지고 되돌릴 수 없어요.
  함께 만든 분들도 더 이상 볼 수 없어요.

  다른 분의 앨범에 남긴 사진 12장은
  그 앨범이 비어 보이지 않도록 이름만 지워져요.

              [ 그만두기 ]   [ 탈퇴하기 ]
```

- **`그만두기` 가 왼쪽이고 기본**이다. 되돌릴 수 없는 일이라 실수로 눌리면 안 된다.
- `영구 복구 불가능합니다` 같이 쓰지 않는다 → **`되돌릴 수 없어요`**(§8).
- **새 페이지를 만들지 않는다.** 이미 있는 시트·딤을 쓴다(§11).
- 해당 없는 줄은 **안 보인다.** 남의 앨범에 남긴 것이 없으면 그 문단이 없다.
- ★ **확인창을 한 번만 둔다.** 두 번 묻지 않는다. 한 번이면 충분하고 두 번은 무례하다.

### 서버 — 순서

★ **권한과 판정은 전부 백엔드에서**(§10). 프런트가 보내는 숫자를 믿지 않는다.

```
① 셀 때 (탈퇴 화면을 여는 순간)
   내가 만든 앨범 수 · 그 앨범들의 사진 수
   남의 앨범에 내가 올린 사진 수
   ★ 세는 식은 한 곳에 둔다. 화면마다 따로 세지 않는다(§1)

② 지울 때 — 한 트랜잭션
   1. 내가 owner_id 인 앨범을 지운다
      → K-2 가 CASCADE 로 바꿔 놨으므로 자식은 DB 가 알아서 지운다
      → 자식 열거를 다시 쓰지 않는다
   2. album_contributors.display_name 을 비운다
      ★ user_id 는 SET NULL 되지만 이름은 글자로 저장돼 있어 남는다.
        이것을 안 지우면 "이름만 지워져요" 가 거짓말이 된다
   3. album_members · family_members · family_invitations 의 내 행을 지운다
      (RESTRICT 를 푸는 자리다)
   4. profiles 를 지운다 → SET NULL 들이 여기서 끊긴다
   5. auth.users 를 지운다
      ★ 안 지우면 같은 카카오 계정으로 다시 가입할 수 없다

③ Storage
   ★ 지운 앨범의 파일을 **실제로 지운다.** 여기서는 지운다.
     K-3 에서 세기만 만든 것은 **자동 정리**라 위험했기 때문이다.
     탈퇴는 사용자가 직접 누른 것이고, 지운다고 화면에서 약속했다.
     약속하고 안 지우면 거짓말이고, 개인정보를 안 지운 것이 된다.
   · 파일 삭제가 실패해도 DB 트랜잭션은 되돌리지 않는다(묶을 수 없다 — K-3).
     실패한 경로를 기록에 남긴다. K-3 의 세기가 나중에 잡는다.
```

### 하지 말 것

- **남의 앨범의 사진·한 줄을 지우지 않는다.** 이름만 끊는다.
- **소프트 삭제로 대신하지 않는다.** `deleted_at` 만 찍고 데이터를 남기면 탈퇴가 아니다.
- FK 를 더 바꾸지 않는다. `RESTRICT` 넷은 **탈퇴 코드가 순서대로 지워서** 푼다.
  CASCADE 로 바꾸면 다른 곳에서 사람이 지워질 때 앨범이 조용히 사라진다.
- 확인을 두 번 묻지 않는다. 비밀번호·이메일 재입력을 요구하지 않는다.

### 회귀 테스트

- 앨범이 있는 사람도 탈퇴가 **성공**할 것
- 탈퇴 뒤 **남의 앨범의 내 사진이 그대로 있을 것** · `contributor_profile_id` 가 비고
  `album_contributors.display_name` 도 비어 있을 것
- 탈퇴 뒤 내가 만든 앨범과 그 사진 행이 **없을 것**
- 숫자를 세는 곳이 **한 곳**일 것
- 프런트가 보낸 숫자를 서버가 쓰지 않을 것

| 담아두기 | 이 앨범을 담아둘까요? | 담아두면 다음에도 이 앨범을 찾을 수 있어요. |
| 게스트 저장 | 이 앨범을 내 앨범으로 저장할까요? | 저장해 두면 다음에도 이 앨범을 찾을 수 있어요. |
| 그 밖 | 로그인 | (설명 없음) |

- ★ **두 벌로 만들지 않는다.** `LegalConsent` 처럼 한 컴포넌트에 값만 넣는다.
- 약관 체크와 `카카오로 계속하기` 는 **모든 경우에 그대로** 있다.
- 제목을 고르는 곳은 **한 곳**이다. 화면마다 문자열을 흩지 않는다.

★ K-14(약관 동의)는 보류됐다. **K-21 은 혼자 해도 된다.**

## K-22. 🔴 초대 링크로 들어와 로그인하면 첫 화면으로 떨어진다 — **크기: 보통**

### 실기기 (2026-08-10)

초대 카톡 메시지 → `함께 만들기` → 초대장 화면 → `카카오로 계속하기` → 로그인 성공
→ **첫 화면으로 간다.** 초대장을 다시 보려면 **카톡으로 돌아가 메시지를 또 눌러야** 한다.

★ 이건 **참여를 자동으로 잇는 것이 아니다.** §1 의 *"로그인했다는 이유로 참여자를
만들지 않는다"* 와 충돌하지 않는다. **원래 보던 화면으로 돌아오기만** 하면 된다.
이름은 여전히 사람이 적는다.

### 원인 (★ 짐작이다 — 로그로 갈라라)

`authService` 에 돌아갈 자리를 두는 길이 **둘**이다.

```
① sessionStorage  RETURN_TO_KEY          ← persistReturnTo
② 콜백 주소의 ?returnTo=                  ← oauthCallbackRedirectUrl
```

**①은 K-9 에서 이미 죽는 것이 증명됐다** — 카카오 로그인 왕복에서 화면이 통째로
다시 뜨면서 `sessionStorage` 가 사라진다(24차 §11). 그러면 ②가 받아야 하는데
그것도 안 되고 있다.

갈라라 — **콜백에 실제로 도착한 주소 전체**를 본다.

```
/auth/callback?returnTo=... 가 붙어 있는가?
  붙어 있는데 안 가면  → 읽는 쪽(consumeReturnTo)이나 safeReturnTo 가 떨어뜨린 것
  안 붙어 있으면       → 만드는 쪽이거나, 중간에 누가 지운 것
```

★ 도메인 이전(2026-08-10) 뒤에 나온 증상이면 **`www` 와 apex 사이의 넘김**도 본다.
초대 링크가 `www.woorialbum.com/join/...` 으로 나간 적이 있다.

### 고칠 것

- 로그인하고 돌아오면 **누르기 전에 보던 그 화면**으로 간다.
- ★ **돌아갈 자리를 `sessionStorage` 에만 두지 않는다**(24차 §11).
  K-9·K-15 가 쓰는 `localStorage` 장치를 그대로 쓴다. **새로 만들지 않는다.**
- 참여를 자동으로 하지 않는다. 이름 칸이 있는 그 화면으로 돌아오는 것까지다.
- 돌아온 뒤 이름 칸은 지금처럼 프로필 이름으로 채운다. 그 동작은 그대로다.

### 회귀 테스트

- `/join/<token>` 에서 로그인하면 돌아갈 자리가 `/join/<token>` 일 것
- `sessionStorage` 가 비어 있어도 그럴 것 ← **이것이 핵심이다**
- 다른 출처(`/s/<token>` · 첫 화면)도 각각 제자리로 돌아올 것

## K-23. 🔴 한마디가 화면에서 캡션처럼 보인다 — **크기: 보통 · 여러 번 나온 것**

★ **J-1 때부터 여러 번 나왔고 매번 못 잡았다. 저장 쪽만 봤기 때문이다.**

### 저장은 맞다 (2026-08-10 개발 DB 실측)

```
photo_memories
  comment      "귀요미"
  author_name  "둘째"
  photo_id     3f12027c

album_photos (3f12027c)
  caption      ""        ← 비어 있다
```

서버 응답도 맞다 — `album.py:1622~1630` 이 `caption` 과 `comments` 를 갈라서 내려주고,
`AlbumPhotoUrlResponse`(`schemas.py:42~`)에 둘이 따로 있다. 주석에 §7 3계층이라고 적혀 있다.

★ **틀린 곳은 화면이다.** `comments` 를 캡션 자리에 그리거나, `comments` 를 그리는 자리가
아예 없어서 캡션처럼 보이는 것이다.

★ 겉으로는 똑같아 보인다 — 한마디가 **작성자 이름 없이 사진 밑 한 줄**로 뜨기 때문이다.
§7 대로면 이름과 함께 나와야 한다.

### 먼저 확인하고 보고한다 (짐작으로 고치지 않는다)

```
1) 앨범 상세와 공유 화면이 응답의 comments 를 실제로 쓰는가?
   쓴다면 어느 자리에, 어떤 모양으로 그리는가?
2) 그 자리가 캡션 자리와 구분되는가? 작성자 이름이 붙는가?
3) AlbumRenderer(화면·공유·PDF 가 같이 쓰는 것)에서는 어떻게 되는가?
```

### 고칠 것 (SCREEN_SPEC §7 · §9)

- **캡션**은 사진 아래 한 줄이고 **인쇄된다.** 작성자 이름이 붙지 않는다.
- **한마디(`comments`)** 는 캡션과 **다른 자리**다. **작성자 이름과 함께** 보인다.
- 두 계층이 화면에서 구분되어야 한다. 같은 자리에 같은 모양으로 그리지 않는다.

### 하지 말 것

- **백엔드를 건드리지 않는다.** 응답은 이미 맞다.
- **저장 경로를 건드리지 않는다.** DB 는 정확하다.
- 캡션 렌더를 다시 만들지 않는다. **한마디 자리만** 본다.

### ★ 이번에 배운 것

**증상이 "저장이 잘못됐다" 처럼 보여도 저장을 먼저 의심하지 않는다.**
DB 를 한 번 보면 5분이면 갈린다. 그동안 저장 쪽만 뒤져서 세 번 놓쳤다.
